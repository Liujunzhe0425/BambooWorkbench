# 框架适配请求：售后强制 AI 接入页与框架托管调用适配器

## 1. 业务目标与使用场景

售后人员点击进入售后模块后，第一屏必须直接进入售后专用的 AI 接入页，而不是先进入文件选择、
离线分析页或要求用户去公共设置中预先配置。用户在该页完成 AI Provider、接口地址、模型和
API Key 输入，连接验证成功后才能继续本批次售后分析：

```text
进入售后模块
-> 售后 AI 接入页输入 API Key 并选择 Provider/模型
-> 测试连接成功
-> 选择 Excel
-> 查看脱敏预览并明确授权本批次联网
-> 框架 AI 适配器调用所选 Provider
-> 售后模块接收结构化 AI 建议
-> 用户逐文件复核售后费用、责任工厂和投诉类型
-> finalize 生成 Excel、JSON、图表和报告
```

本请求所称“售后模块直接开始 AI 分析”是用户交互效果，不代表模块进程持有 Provider
API Key 或自行访问外部模型。外部 HTTP 请求必须由主框架托管的 AI 适配器执行。

售后标准任务必须使用 AI：用户不能在正常入口选择“跳过 AI”或“仅离线分析”。没有有效
API Key、连接测试未通过或用户未完成本批次联网授权时，不创建售后分析任务；已有凭据也必须先
进入该页显示掩码状态并由用户确认后才能继续。任务开始后若 Provider 中途失败，仍按工作台安全
要求生成完整离线降级结果，避免丢失任何 Excel；该降级是故障兜底，不是正常可选运行模式。

现有售后业务实现、字段抽取、分类规则、费用口径、逐文件人工复核、年度汇总、图表和报告
保持不变。本次只申请框架提供统一、安全的调用适配层和任务编排。

## 2. 当前限制

售后模块当前分支保留了 1.6.4 的业务实现，也保留了模块本地 AI 通道。静态核对可见：

- `src/after_sales_agent/cli.py` 仍导入 `module_ai_config.py`，draft 在特定环境开关下会读取
  Windows keyring；
- `extractor.py`、`llm_analyzer.py` 和 `deepseek_gateway.py` 仍可由模块进程直接调用外部
  Provider；
- `ai_service.py` 已有脱敏请求构造、框架响应校验和降级辅助函数，但当前 CLI 尚未把它们完整
  接入 draft/finalize，`result.json` 初始化的 `service_requests` 仍为空数组。

上述本地 AI 通道用于说明独立版本已经实现的业务效果，不符合当前工作台的凭据和联网边界，
因此不能按现状合入 `integration`，也不能把 `requires_network: false` 解释为已经完成整改。
本 FCR 的目的，是先由框架提供等价适配能力，再只替换 AI 传输和编排通道，保留售后业务实现。

现有框架公共流程也不能完整复现售后独立版本的使用顺序：

- 当前公共流程可能先展示业务确认，再执行 AI 服务，复核人员无法先看到 AI 建议；
- 多个 AI 请求可能生成多个授权项，批量任务操作成本高；
- Provider、模型和 API Key 只能在公共设置中管理，进入售后模块时不会先出现强制的专用接入页；
- 旧的 `FCR-after_sales-20260723-module-local-ai-config.md` 曾提出由模块读取 Windows 凭据并
  直接访问 Provider，该设计违反最新边界，现已废止，不能作为实施依据；
- 在没有获批公共适配器之前，模块本地网关、环境开关和 keyring 读取不得在工作台启用、分发或
  作为合并依据；售后模块 PR 保持 Draft。

## 3. 请求的框架改动

### 3.1 页面与交互

- 页面/区域：用户点击售后模块后首先进入框架实现的售后 AI 接入页；连接通过后才进入售后文件
  选择与任务创建页。实现代码归框架所有，不放入 `modules/after_sales/`。
- 必须控件：Provider、HTTPS Base URL、模型、API Key，以及“测试连接”和
  “开始智能分析并进入人工复核”。
- 强制门禁：首次使用必须输入 API Key；已有凭据只显示已配置状态和掩码尾号。API Key 缺失、
  格式无效或测试连接失败时，“继续选择 Excel”不可用，不得自动切换成离线任务。
- 模型选择：支持框架已有 Provider 的模型列表；手工模型名必须经过非空、长度和字符校验。
- 凭据展示：只显示“已配置/未配置”和掩码尾号，不得把完整 API Key 回填到界面。
- 用户操作顺序：进入售后 -> 配置并验证 API -> 选择文件 -> 查看脱敏预览 -> 点击开始并授权
  当前批次 -> 查看 AI 进度 -> 逐文件人工复核 -> 生成正式成果。
- 授权语义：点击开始只能授权当前任务；更换文件、Provider、接口地址或模型后必须重新确认。
- 加载状态：显示请求批次数、已完成批次数、降级文件数，不展示内部请求 JSON 或 API Key。
- 开始前错误：无密钥、格式错误或测试连接失败时停留在接入页，不创建任务、不读取 Excel、
  不提供“跳过并离线开始”入口。
- 运行中错误：任务授权并开始后发生超时、限流、余额不足、模型不存在或响应不合法时，显示
  结构化错误并继续离线复核；不得丢弃任何已成功解析的 Excel。
- 结果展示：每份文件显示 AI/离线来源、原因摘要和候选投诉类型；售后费用、责任工厂和最终
  投诉类型仍必须由用户确认。
- AI 辅助范围：保留独立版已有的品牌候选、问题类型、具体原因、费用候选、责任工厂候选和
  处理状态候选分析；其中费用、责任工厂、责任认定、赔偿和结案等受控字段只能作为建议，
  不得越过确定性证据和人工复核写成最终结论。
- 覆盖范围：每个成功解析的 Excel 都必须生成 AI 请求，不只处理规则含糊或多标签案件；AI
  响应返回并绑定后才展示逐文件人工复核。损坏或无法解析的文件只保留失败对账行，不伪造请求。

### 3.2 接口与合同

- 目标模块输入/输出：复用现有 `job.json`、`result.json`、`service_requests`、
  `service-response.json` 和 `confirmation.json` 合同；当前 CLI 的缺失接线在框架适配获批后
  通过售后模块的最小兼容提交完成。
- 适配器输入：模块 draft 结果中的 AI `service_requests`，以及框架任务上下文中的用户授权、
  Provider 和模型选择。
- 适配器输出：继续使用现有 `service-response.json` 信封；响应按 `request_id` 和模块请求内的
  稳定案件标识绑定。
- 推荐工作流：

```text
draft 生成脱敏 service_requests
-> 框架一次授权并执行服务
-> 框架触发 AI 建议绑定/复核准备步骤
-> 展示逐文件业务确认
-> finalize 消费 confirmation_file 和 service_response_file
```

- 优先由框架内部状态机实现，不改变现有 Schema。若确实需要新增阶段或字段，必须是可选字段，
  同步 Schema、Pydantic 模型、示例和兼容测试，并允许旧模块继续按原流程运行。
- 模块进程不得获得真实 Provider API Key。若框架需要任务级能力令牌，该令牌必须是短时、
  单任务、不可用于直接访问外部 Provider 的框架内部令牌，且不得进入结果、日志或历史数据库。
- 退出码和任务最终状态保持现有合同；AI 失败是业务降级，不等于文件处理失败。
- 模块能力声明：框架适配落地后的模块兼容提交应把 `module.json.requires_network` 改为 `true`，
  表示售后标准工作流必须先通过联网门禁。若框架需要更精确地区分“框架服务必需”和“模块进程
  自身联网”，请在独立框架 PR 中增加向后兼容的正式合同字段，不得由模块私自添加未定义字段。

### 3.3 公共服务、存储或打包

- 所需能力：在框架侧增加或扩展 `AfterSalesAiAdapter`，复用现有 Provider、脱敏预览、
  用户授权、超时、重试、限流和审计能力。
- 外部调用主体：只能是框架 AI Provider/适配器，不能是售后模块 CLI、便携模块 EXE 或
  模块内旧网关。
- API Key 保存：继续由框架写入 Windows 安全凭据；不写 SQLite、任务目录、模块配置、
  环境持久化、日志、安装包或 Git。
- 非密钥配置：Provider、Base URL 和模型可由框架保存；历史任务只记录必要的 Provider/模型
  标识和授权结果，不保存密钥或完整外发正文。
- 安装版/便携版：适配器和 Provider 必须随主程序打包，不依赖系统 Python、开发 `.venv` 或
  售后独立网站服务。
- 降级行为：无密钥、连接测试失败或用户未授权时任务不开始；任务开始后的离线、超时、限流、
  服务错误或响应校验失败，模块保留全部输入记录并生成完整离线结果。

## 4. 责任边界

- 模块方已经完成：售后 Excel 解析、确定性规则、多标签候选、三项必审、finalize 写回和全部
  业务输出；`ai_service.py` 已有脱敏请求构造、响应校验和逐文件降级辅助实现。
- 本次模块方不修改：现有业务算法、费用口径、Excel/JSON/图表/报告文件集合和人工优先级。
- 等待框架提供：进入售后即显示的强制 AI 接入页、凭据托管、连接测试、任务启动门禁、一次
  授权、AI 适配器、服务先于业务复核的编排、进度和错误展示。
- 仍由模块方负责：请求 payload 的业务字段、候选编号、响应业务校验、规则降级和输出正确性。
- 框架适配合入后模块方负责的最小改动：把 `ai_service.py` 接到 CLI 的 draft/finalize，删除模块
  keyring 读取、Provider HTTP 网关及相关打包依赖；不得改动上述业务算法和输出口径。
- 需要人工确认：售后费用、责任工厂、最终投诉类型，以及责任认定、赔偿、审批和结案等权限性
  结论。
- FCR 获批前：模块默认离线能力可用于开发验证，但包含本地直连通道的当前 PR 不得合并；不得
  设置启用开关、读取真实凭据或发起真实外部请求。

## 5. 数据、安全与权限

- 外发内容仅限分析所需的脱敏摘要、候选类型、证据编号和必要产品上下文。
- 禁止发送客户名称、联系人、电话、邮箱、地址、销售人员、本地路径、原始文件名、Excel
  二进制、API Key 和完整工作簿正文。
- 框架必须在联网前展示脱敏预览；用户未授权时外部网络调用次数必须为 0。
- API Key 只允许框架凭据服务读取；模块、自检、测试和 finalize 均不得读取。
- 日志、错误、崩溃报告、任务 JSON、SQLite、输出文件和安装包中不得出现 API Key 或模型原始
  响应。
- AI 无权决定费用、责任工厂、责任认定、赔偿、审批或结案状态。
- 本请求及其验收材料只使用完全虚构的脱敏样例，不引用真实姓名、客户文件名、金额或案件特征。

## 6. 兼容性与迁移

- 是否破坏现有合同：否；如框架评估必须扩展合同，只接受可选且向后兼容的扩展。
- 是否兼容当前正式模块：框架适配器未实现时保留现有版本的离线开发验证能力；适配器落地后的
  正式售后入口改为 AI 强制前置，不再提供用户主动选择的离线标准流程。
- 旧任务和历史数据：不自动重跑 AI；按任务创建时的合同和授权状态打开。
- 其他模块：水分和水煮现有流程默认不变；公共能力必须通过显式声明或模块 ID 定向启用。
- 框架尚未升级时：售后模块仍可用于离线开发验证，但不能作为满足本次产品要求的正式入口；
  当前含本地 AI 通道的模块提交不得进入 `integration`。
- 迁移：旧的售后专属 keyring 方案不迁移、不读取；如开发机曾保存旧测试凭据，由负责人在框架
  外人工删除，不能由模块扫描凭据库。
- 回滚：回退到上一正式售后入口并停止创建新售后 AI 任务；已开始任务仍可离线降级完成，业务
  数据无需迁移。不得通过回滚重新启用模块本地 keyring 或直联网关。

## 7. 验收标准

1. 点击售后模块后，第一屏直接显示售后 AI 接入页；没有有效 API Key 或连接测试未通过时，
   不能进入文件选择，也不存在“跳过 AI”入口。
2. 给定一批完全虚构的脱敏售后 Excel，用户完成 API 配置、选择 Provider 和模型、查看脱敏预览
   并点击开始后，框架只产生一次本批次授权记录。
3. 网络抓包或 Provider 测试桩证明外部请求由框架进程发出；售后模块进程没有访问外部模型地址，
   也没有读取 Windows 凭据。
4. API Key 不出现在任务目录、SQLite、日志、异常、结果 JSON、Excel、报告、安装包和 Git
   变更中。
5. 至少存在一个成功解析文件时，框架在人工复核前必须实际尝试至少一次 Provider 调用；每个
   成功解析文件都包含在 AI 请求中，不能只对含糊案件调用。
6. AI 返回后再展示逐文件人工复核；每份文件至少包含售后费用、责任工厂和投诉类型三项必审，
   最终全部输出使用人工值。
7. 用户在任务开始前拒绝联网时外部调用次数为 0 且不创建任务；任务已开始后 Provider 失败时，
   所有成功解析文件仍进入离线复核并生成完整成果。
8. 任一请求超时、限流、模型不存在、响应缺失或 JSON 非法时，只降级受影响请求；输入文件对账
   数量保持完整，未知费用不写成 0。
9. `finalize` 阶段外部网络调用次数为 0；重复 finalize 不重复统计、不重复调用 AI。
10. 切换框架已支持的 Provider 或模型不需要修改售后模块业务代码。
11. 水分、水煮和旧版售后模块现有合同及任务回归通过。
12. Windows 便携版在无系统 Python、无开发 `.venv` 环境下完成配置、授权、AI 降级、人工复核
    和正式导出。
13. 框架适配器失败不会使桌面程序退出，不留下失控子进程或把半成品登记为成功。
14. FCR 未获批准和框架独立 PR 未合入前，售后模块 PR 保持 Draft 且不得合并。

## 8. 备选方案与影响

- 已考虑：模块直接读取 keyring 并调用外部 Provider。
- 不采用原因：会绕过框架凭据托管、脱敏预览、授权、审计和故障隔离，并导致模块清单与联网
  行为不一致。
- 已考虑：恢复售后独立网站服务。
- 不采用原因：产生第二套界面、端口和运行时，无法纳入工作台历史、安装和统一权限边界。
- 已考虑：继续当前服务后置流程，不增加适配器。
- 影响：安全可用，但人工复核看不到调用后的 AI 建议，不能满足售后人员的目标操作顺序。
- 预计框架影响：`core/tasks/`、AI Provider/服务编排、凭据服务、售后任务页和相关集成测试。
- 预计模块影响：本请求阶段只修改文档；框架合同获批后另行在模块分支提交最小协议适配，删除
  模块凭据/直联网关并接入框架响应，不改变售后业务算法和输出口径。
- 风险：多阶段任务恢复、重复提交幂等、批量请求部分失败、凭据泄露和旧任务兼容，需要自动化
  测试覆盖。
