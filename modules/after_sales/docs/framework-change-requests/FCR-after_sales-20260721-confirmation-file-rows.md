# 框架适配请求：每份 Excel 的人工复核项集中显示在独立行

## 1. 业务目标与使用场景

售后人员一次可能导入 1 至 100 份 Excel。售后分析模块会为每份成功处理的 Excel 生成“售后费用、责任工厂、投诉类型”三项必审内容，并可能同时生成该文件的其他字段歧义确认。

人工复核时，用户必须清楚知道每一组输入框属于哪一份 Excel，避免在连续长表单中把相邻文件的费用、责任工厂或投诉类型填错。期望全局“待确认事项”页面按 Excel 文件显示独立的复核行：一个源文件对应一行（或一张横向卡片），文件名作为该行标题，该文件的全部复核控件集中放在同一行内。完成一份文件的整行复核后，用户再处理下一行；不允许把不同 Excel 的同类字段连续混排。

## 2. 当前限制

当前实现位于 `ui/pages/confirmations_page.py`：

- `_render()` 逐条遍历 `ConfirmationPrompt`，并把所有确认项加入同一个 `QFormLayout`；
- 页面只有一个外层 `card`，没有根据 `prompt.source.source_file` 分组；
- 文件名仅在每个字段下方的“来源”小字中重复显示，连续导入多份 Excel 时无法快速辨认文件边界；
- 当前标签使用 `field 1/3`、`field 1/9` 这类跨文件全局编号，容易让用户误以为同一 Excel 的复核项被拆散；
- 售后模块现有输出已按输入文件顺序连续返回确认项，并在每条确认项的 `source.source_file` 中提供原始 Excel 文件名，统一结果合同也已经包含该字段，无需模块新增私有页面或更改合同。

复现步骤：

1. 在售后分析模块一次导入至少 5 份 Excel；
2. 运行分析并进入“待确认事项”；
3. 页面把全部确认项连续显示在同一表单中，标签按字段全局计数，无法直观看出每份 Excel 的完整复核范围。

## 3. 请求的框架改动

### 3.1 页面与交互

- 页面/区域：全局 `ConfirmationsPage` 的确认内容区域。
- 必须具备：
  1. 使用 `ConfirmationPrompt.source.source_file` 对当前任务的确认项稳定分组；
  2. 每个不同的 Excel 文件显示为一条独立复核行或一张横向 `QFrame` 复核卡片；
  3. 每行左侧或顶部固定显示“第 N 份 / 共 M 份”和完整文件名；
  4. 同一 Excel 的全部确认项必须集中在该行内横向排列，至少清楚显示字段名称、编辑控件和必填/可选状态；售后模块中包括售后费用、责任工厂、投诉类型以及该文件自身的日期、金额歧义等其他确认项；
  5. 不同 Excel 的确认控件不得按字段类型跨文件混排，不再显示 `售后费用 1/9`、`complaint_date 1/3` 这类跨文件编号；如需要编号，只显示文件内序号；
  6. 相邻文件行之间使用可见边框、圆角、背景色、上下间距或分隔线，不能仅靠字段下方的来源小字区分；
  7. 仍使用页面底部统一的“提交确认”按钮，一次提交当前任务全部答案；
  8. 保留现有 `answer_inputs`、`batch_checks`、`remember_checks` 与 `confirmation_id` 的一一对应，不能因分组改变提交值；
  9. 文件很多时按文件行纵向滚动；单行字段较多时允许行内响应式换行或横向滚动，但绝不能把该文件的字段移到其他文件行中。
- 建议视觉：
  - 文件行标题区域使用浅竹青背景，文件名使用较粗字体；
  - 文件行外框使用与现有主题协调的绿色或灰绿色实线；
  - 相邻文件行垂直间距不少于 12 像素；
  - 行内字段使用紧凑列布局，字段名位于控件上方，不重复显示同一个来源文件名。
- 无来源文件的兼容处理：将 `source_file` 为空的确认项放入最后一张“其他确认事项”卡片，不能丢弃。
- 空状态与错误状态：沿用当前页面行为；分组渲染失败时不得提交不完整答案。

### 3.2 接口与合同

- 当前输入：`list[ConfirmationPrompt]`，其中已有 `source.source_file`。
- 期望输入：不变。
- 当前输出：`list[ConfirmationAnswer]`。
- 期望输出：不变。
- 新增或修改字段：无。
- 退出码/状态变化：无。
- 旧模块兼容方式：水分、水煮和旧版售后模块均按已有 `source_file` 自动分组；无需迁移模块结果 JSON。

### 3.3 公共服务、存储或打包

无新增公共服务和存储需求。安装版、便携版均应使用同一分组页面；不得引入联网依赖或系统 Python 依赖。

## 4. 责任边界

- 模块方已经完成：
  - 每份成功处理的 Excel 均输出售后费用、责任工厂、投诉类型三项必审确认；
  - 每条确认项均携带准确的 `source.source_file`；
  - 禁止三项业务复核跨文件批量套用；
  - 人工答案可正确写回最终 Excel 和年度汇总。
- 等待框架提供：全局待确认页面按 `source_file` 分组并渲染独立卡片。
- 仍由模块方负责的业务逻辑：复核字段、建议值、费用校验、责任工厂推断、投诉类型选项和最终 Excel 写回。
- 需要人工确认的结论：每份 Excel 的售后费用、责任工厂、投诉类型。

## 5. 数据、安全与权限

- 仅在本地展示模块已返回的源文件名和确认内容；不新增数据采集、联网或 API 密钥处理。
- 文件名可能包含客户或项目名称，页面不得上传、外发或写入新增日志。
- 卡片分组只影响显示，不得自动替用户确认或把答案应用到其他文件。

## 6. 兼容性与迁移

- 是否破坏现有合同：否。
- 是否兼容当前正式版模块：是。
- 旧任务和历史数据如何处理：重新打开待确认任务时按已有 `source_file` 分组；原确认答案结构不变。
- 如果框架尚未升级，模块能否继续运行：能，但仍使用连续长表单，无法满足本次可用性要求。
- 回滚方式：回退框架分组渲染提交；模块端无需回滚。

## 7. 验收标准

1. 给定 5 份 Excel、每份 3 项确认，页面显示 5 条独立文件复核行，而不是 15 个无分隔连续条目；
2. 每行标题包含对应 Excel 完整文件名，并显示“第 N 份 / 共 5 份”；
3. 每行内准确集中显示该文件的售后费用、责任工厂、投诉类型三个编辑控件，不能混入其他文件的字段；
4. 同一文件另有日期、企业承担金额等歧义项时，这些控件也必须留在该文件行内；
5. 页面不再出现跨文件的 `字段 1/9` 编号；
6. 修改任意两行中的不同答案后提交，生成的 `ConfirmationAnswer.confirmation_id` 和值与原输入控件逐项对应；
7. 给定 100 份 Excel，页面可按文件行纵向滚动到最后一行，输入控件大小正常；
8. 给定一个没有 `source_file` 的旧确认项，页面显示“其他确认事项”行且该项可正常提交；
9. `tests/ui/test_confirmation_usability.py` 增加按文件分组、行内集中展示、答案映射和大量文件滚动测试并通过；
10. 完整便携版执行 `--smoke-test` 和 `--demo-smoke-test` 均返回 0；
11. 不修改统一模块合同，售后模块 1.4.0 的 draft → finalize 流程继续通过。

## 8. 备选方案与影响

- 已考虑的替代方案：在模块字段名称或原因文本中反复拼接文件名；为售后模块单独建立私有复核窗口；把一份文件的三项复核合并成一个字符串字段。
- 未采用原因：上述方案不能形成清晰视觉分隔、会破坏通用工作台体验，或会降低结构化答案和校验能力。
- 影响的框架目录/功能：预计仅涉及 `ui/pages/confirmations_page.py`、主题样式及对应 UI 测试。
- 影响的其他模块：水分和水煮确认项也会按来源文件获得更清晰分组，合同与业务逻辑不变。
- 预计风险：低至中；主要风险是重构布局后答案控件映射、可访问性名称或滚动高度回归，需由自动化 UI 测试覆盖。
