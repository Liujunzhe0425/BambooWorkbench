# 竹丝水分模块 — 业务规则与数据说明

> 本文档是模块当前业务口径的**唯一权威位置**。
> 不包含架构、测试命令或验收清单。

---

## 1. 字段映射（输入 Excel 字段 → 内部模型）

### 1.1 输入载体

- 输入为 `.xlsx` 工作簿。
- 每个工作簿接受 **1—10 个有效样本**；11 个及以上使当前文件失败，不截断。
- 损坏文件只影响自身，不影响同批次其他文件。
- 文件名以 `~$` 开头的 Excel 临时文件必须跳过。
- 内容 SHA-256 完全相同的后续文件跳过（只计算第一次出现的文件），输入读取前后会复核内容指纹。
- 正式运行不修改输入文件。

### 1.2 识别字段

模块从工作簿中动态识别以下业务字段：

| 业务字段 | 说明 |
|---|---|
| 供应商 | 供应方身份 |
| 物料类型 | 竹丝 / 原竹丝 |
| 来料日期 | 到货日期；历史工作簿中“到货时间”按同一字段读取 |
| 检测日期 | 检测执行日期 |
| 总重量 | 来料总重 |
| 取样部门 | 执行取样的部门 |
| 初始质量 | 烘干前样本质量 |
| 烘干质量 | 烘干后样本质量 |
| 锡纸质量 | 包裹样本的锡纸质量 |
| 相对含水率 | Excel 中已记录的含水率值（用于与公式复核值比对） |

### 1.3 历史月度工作簿兼容

- 兼容标题形如“某供应方原竹丝水分检测”或“某供应方竹丝水分检测”的旧工作簿。
- 仅在显式供应商或物料字段缺失时，才从标题回退提取。
- 只有月、日的历史日期，优先使用模块配置中的 `default_year`；未配置时，可从严格形如 `2026年4月份` 的父目录名推断年份。
- 父目录存在多个冲突年份时拒绝处理，不使用当前年份或文件修改时间猜测。
- Excel 含水率与公式复核值在容差 `0.0001` 内视为一致，不因浮点尾数产生确认。

### 1.4 歧义处理

- 多个工作表得分相同且无法唯一确定时，返回结构化歧义记录，draft 可据此生成业务 confirmation。
- 已唯一识别的工作表、表头和值不要求用户重复输入。
- 缺字段、损坏 workbook 和格式变化必须形成文件级结构化结果。

## 2. 含水率公式

### 2.1 公式定义

```
含水率 = (初始质量 - 烘干质量) / (初始质量 - 锡纸质量)
```

- 计算全程使用 `Decimal`，不得为方便序列化而提前转为 float。
- 阈值比较同样使用 `Decimal`。

### 2.2 原值与复核值

- 源表含水率必须读取，同时根据源始末重量独立复核公式。
- 原始值、复核值和最终统计采用值**分别保留**，不能用写回 Excel 的方式“修正”原值。

三种情形下的取值规则：

| 情形 | 行为 |
|---|---|
| 原始值与复核值一致（容差 0.0001 内） | 使用原始值 |
| 无缓存原始值 | 使用可复核值 |
| 两者冲突且业务值不明确 | draft 生成 confirmation，finalize 应用答案后重新计算 |

### 2.3 容差

- 公式复核容差为 **0.0001**。
- 原始含水率与复核值差异在此容差内视为一致，不因浮点尾数产生 confirmation。

## 3. 统计口径

### 3.1 统计指标

对每个工作簿的有效样本，计算以下统计量：

| 指标 | 说明 |
|---|---|
| 样本数 | 有效样本个数 |
| 均值 / 总均值 | 所有样本含水率的算术平均 |
| 最大值 | 样本含水率的最大值 |
| 最小值 | 样本含水率的最小值 |
| 极差 | 最大值 - 最小值 |
| 样本标准差 | 样本标准差（单样本时为不可用值，不伪造为零） |
| 中位数 | 排序后居中值 |
| 四分位数 | Q1（下四分位数）、Q3（上四分位数） |
| IQR | 四分位距（Q3 - Q1） |
| 部门均值 | 按取样部门分组的含水率均值 |
| 部门均值最大差 | 各部门均值之间的最大差值 |

### 3.2 单样本标准差

- 仅一个有效样本时，标准差为**不可用值**，不得伪造为零。

### 3.3 计算精度

- 所有统计计算使用 `Decimal`，统计算法口径以旧通过测试为基线，不为重构而重写。

## 4. 规则与阈值

### 4.1 规则加载

- 规则从模块内只读发布包加载。
- `rules.yaml` 精确字节 SHA-256 在加载时校验，运行期间不能发布或修改规则。
- 规则必须包含：编号、版本、来源、适用范围、规则文件 hash 和确认状态。

### 4.2 规则状态与自动判定

- 只有 `confirmed` 规则可自动判定。
- `pending_confirmation` 规则只能生成确认或说明，不能自动判定。

### 4.3 当前筛查阈值

| 阈值 | 方向 | 材料范围 |
|---|---|---|
| **0.55** | 偏高筛查 | 竹丝 / 原竹丝 |
| **0.47** | 偏低筛查 | 竹丝 / 原竹丝 |

> **状态：待业务批准。** 上述阈值是从旧业务基线迁移而来的默认筛查阈值，当前标注为 **待业务批准**，不得称为正式生产标准、已批准阈值或 confirmed 生产规则。命中阈值只形成橙/绿筛查提示，不构成不合格、责任、处罚、放行或处置结论。

> **当前运行差异：** 已交付机器规则包仍将这两个阈值标记为 `confirmed` / `default-v1-approved`，因此当前运行时会执行筛查。这是待治理的不一致，并不构成业务批准证据；在规则资产完成受控更新前，运行结果只能作为待批准阈值产生的筛查提示。详见《验收标准与已知限制》和 `framework-issues.md`。

### 4.4 规则包变化

draft 与 finalize 的规则 hash 不一致时：

- 状态为 `failed`，退出码 0；
- `outputs=[]`、`confirmations=[]`、`service_requests=[]`；
- 顶层 errors 包含 `RULE_PACKAGE_CHANGED_DURING_TASK`；
- 不伪装为颜色 anomaly。

## 5. 橙、绿、红、蓝颜色含义

### 5.1 颜色定义

| Review State | 显示色 | 色值 | 业务含义 |
|---|---|---|---|
| `suspect_high` | **橙** | `F4B183` | 确定性规则支持的偏高疑似 |
| `suspect_low` | **绿** | `A9D18E` | 确定性规则支持的偏低疑似 |
| `high_suspicion_high` | **红** | `FF0000` | 合法且严格匹配的辅助证据支持的高度偏高疑似 |
| `high_suspicion_low` | **蓝** | `5B9BD5` | 合法且严格匹配的辅助证据支持的高度偏低疑似 |
| `normal` | 无 | — | 未命中初筛疑似 |

### 5.2 核心原则

**四种颜色均不是正式错误、不合格、责任或处置结论。** v0.1.0 不为颜色状态使用 `critical`。

- 橙/绿 = 确定性筛查（info 级别），由确定性规则直接判定。
- 红/蓝 = 辅助证据复核（warning 级别），需要合法且严格匹配的结构化辅助证据才能从橙/绿提升。
- 无有效服务/经验依据时，必须保留橙/绿，不得强行提升为红/蓝。

### 5.3 红/蓝提升条件

红/蓝要求以下条件**全部通过**严格校验：

1. request ID 匹配
2. rule hash 匹配
3. candidate ID 匹配
4. direction（偏高/偏低）匹配
5. field 匹配
6. observed value 匹配
7. decision 合法
8. evidence 非空
9. `confidence >= 0.80`

以上任一不满足（包括 `denied`、`error`、`timeout`、缺失、非法 envelope 或普通文本），均保持橙/绿，安全降级。

### 5.4 XLSX 展示映射

主表"竹丝含水率统计"（20列）中，`筛查结果` 列按以下映射显示业务文字：

| 领域状态 | 主表文字 |
| --- | --- |
| `ScreenStatus.NORMAL` | 正常 |
| `ScreenStatus.HIGH` | 偏高疑似 |
| `ScreenStatus.LOW` | 偏低疑似 |
| `ScreenStatus.DATA_QUALITY` | 需人工确认 |

颜色展示规则：

- `筛查结果` 单元格使用 `final_display_color`（橙/绿/红/蓝）作为底色；
- 命中指标属于主表20列时，该指标单元格继续保留既有底色；
- 主表不显示"最终显示色"等文字技术列，技术字段统一在"模型分析记录"工作表展示；
- `DisplayColor.NONE` 不填充底色。

## 6. 人工确认边界

### 6.1 确认生成范围

draft 阶段**只为以下情形**生成业务 confirmation：

- 含水率解释歧义（原始值与复核值冲突且不明确）
- 年份歧义（仅有月日、无法从 default_year 或父目录唯一确定年份）
- 工作表歧义（多个工作表得分相同无法唯一确定）
- 供应商 / 部门映射歧义
- 公式冲突（原值与复核值不一致）
- pending 规则的适用性

**不生成**以下类别的确认：

- 身份、密码、Provider、网络、API Key
- “责任结论”类确认
- 可确定性读取或计算的 Excel 内容
- 已唯一识别的工作表、表头或值

### 6.2 default_year

- 仅有月日的历史日期，优先使用模块配置中的 `default_year`。
- default_year 的确认答案对整批生效（batch_applicable）；已有完整年月日的文件不会被该答案覆盖。
- 未配置 default_year 时，尝试从父目录名（严格形如 `2026年4月份`）推断；存在冲突年份时拒绝处理。

### 6.3 Confirmation ID 生成规则

- draft 根身份为当前 `job.job_id`。
- finalize 根身份为 `job.parent_job_id`（重建 draft 身份）。
- 稳定 confirmation ID 格式：`msr-confirm-<SHA256前24位>`。
- ID 不得依赖 finalize 自身 job_id、绝对路径、执行时间或 UUID。

### 6.4 batch_applicable

- default_year 确认的答案对整批生效。
- 已有完整年月日的文件不会被该答案覆盖。
- confirmation bundle 的 job_id 必须等于 root_job_id。

### 6.5 draft/finalize 确认流转

- draft 存在模块业务 confirmations 时，模块原始状态为 `needs_confirmation`。
- finalize 使用 `parent_job_id` 重建身份，重新运行完整确定性管线，应用 draft 确认答案后重新计算。
- **finalize 不生成新的 confirmations 或 service requests**。
- finalize 输出的 confirmations 和 service_requests 必须为空。

## 7. 经验库边界

### 7.1 运行时只读

- 正式运行时（`run --job`、draft、finalize），经验库**只读**。
- 仅检索同时满足以下条件的结构化经验：
  - 已在 manifest 中登记
  - 哈希有效（未遭篡改）
  - 状态为 `approved`
  - 在有效期内
  - scope 匹配（优先 `moisture`，其次 `shared`）

### 7.2 离线管理隔离

- 离线经验管理端（编辑、审批、发布）与正式运行**严格隔离**。
- `run --job`、draft、finalize 不依赖管理端，不引用未审批或过期经验。

### 7.3 知识文本的使用限制

- 普通知识文本（knowledge plain text）只能作为报告中的指导引用。
- 只有通过结构化经验 Schema 校验的已审核记录，才可能参与复核判定。

## 8. AI 辅助边界

### 8.1 模块定位

- 模块**不直接访问**网络、AI Provider、HTTP、API Key、凭据或主框架数据库。
- 模块只向宿主声明**最小化 service request**，由宿主负责实际调用。

### 8.2 Service Request

draft 阶段最多产生两类请求（各最多一个）：

| 请求类型 | requires_user_consent | 说明 |
|---|---|---|
| knowledge request | `false` | scope 优先 `moisture`，其次 `shared`；query 不超过 200 个 UTF-8 字节 |
| AI request | `true` | `ai_enabled=false` 表示尚未授权，不禁止模块声明业务需要 |

- 两种请求**只在 draft 阶段产生**，finalize 不发起新请求。

### 8.3 AI 候选与 payload 限制

- 每个 AI request 最多 **50 个候选**。
- 规范化 JSON payload 不超过 **65,536 UTF-8 字节**。
- 候选按相对偏离度降序排列，同分时按 candidate_id 升序；超限从末尾移除。
- 未发送候选保持橙/绿状态。
- payload 不得包含：完整 Excel 数据、绝对路径、客户/供应商身份、原始行、API Key 或无边界历史。
- AI request ID 使用 root_job_id、module_id、服务类型和规则 hash，不包含候选摘要，也不使用 finalize 当前 job_id。

### 8.4 Service Response 校验

只有同时满足以下全部条件时，AI 证据才可提升橙/绿为红/蓝：

- request ID、rule hash、candidate ID、direction、field、observed value 全部匹配
- decision 合法
- evidence 非空
- `confidence >= 0.80`

### 8.5 降级行为

以下情况均**安全降级**，保留橙/绿和已完成的所有确定性成果：

- `denied`、`error`、`timeout`
- service response 缺失、不可读或非法
- envelope 不合法或业务 JSON 非法
- 普通文本（非结构化证据）
- confidence < 0.80
- 任一匹配字段不通过

降级规则：

- 服务降级**不丢失**已完成的确定性统计和 artifacts。
- 服务失败通过顶层 errors、analysis_summary 和“模型分析记录”呈现。
- 不自动把基础 `success` 改为 `partial_success`。
- AI 和知识服务**完全不可用**时，模块仍输出确定性的 XLSX、Markdown 和 `result.json`。

## 9. 待业务批准事项

以下事项来源于旧业务迁移基线，当前标记为**待业务批准**，不作为已确认的生产标准：

| 事项 | 当前状态 | 说明 |
|---|---|---|
| 阈值 0.55（偏高筛查） | **待业务批准** | 从旧业务基线迁移的默认值，仅形成橙/绿筛查提示 |
| 阈值 0.47（偏低筛查） | **待业务批准** | 从旧业务基线迁移的默认值，仅形成橙/绿筛查提示 |
| 材料范围“竹丝/原竹丝” | **待业务批准** | 当前阈值适用的材料范围，扩展需业务方确认 |
| 筛查语义边界 | **待业务批准** | 命中阈值的橙/绿提示不得扩张为不合格、责任、处罚或处置结论 |
| 供应商/部门映射固化 | **待业务批准** | 不得根据文件名、历史经验擅自固化映射；有歧义时生成 confirmation |
| 红/蓝辅助证据使用范围 | **待业务批准** | 红/蓝仅为辅助证据提示，不是正式错误或责任结论；是否引入 critical 级别需业务批准 |

> 上述事项以本轮最新业务要求为准。旧文档或代码资产中出现的 `confirmed`、`default-v1-approved` 等机器资产状态仅反映历史开发过程中的内部标记，不代表业务方已正式批准为生产标准。
