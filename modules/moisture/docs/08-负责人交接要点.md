## 2. 负责人必须先知道的结论

1. 模块业务管线已经可用，真实旧格式 Excel 可以成功生成五表 XLSX 和趋势图。
2. 普通桌面启动默认 `use_mocks=True`，不会调用正式水分模块。
3. GUI TaskService 会先快照输入，并把文件改名为 `001-原文件名.xlsx`；历史文件年份只存在于原父目录时，快照会丢失年份上下文。
4. 模块已支持 `module_config_file` 中的 `default_year`，但主框架 `build_draft_job` 当前将该字段固定为 `None`。
5. `0.55/0.47` 阈值尚未批准，当前无颜色是正确治理行为。
6. 主框架 AI 编排当前使用 MockProvider；模块从不直接调用真实 API。
7. 经验只读仓储和离线治理已实现，但当前确定性管线尚未自动查询并附加经验引用。
8. 当前 PyInstaller、便携包和安装验证只包含 Mock 模块，正式水分模块及其完整依赖尚未进入发布运行时。
9. 主框架 CI/`verify_repo.ps1` 不会自动运行 `modules/moisture/tests`，现有全绿证据来自单独执行模块门禁。
10. Knowledge request 能够发出，但 finalize 当前不会把普通 Knowledge 响应写入报告或经验引用。
11. XLSX“来源追溯”会记录绝对路径；本地审计合理，对外分享前必须确认隐私策略。
12. 当前错误弹窗会拼接所有文件的通用错误，批量失败时缺少可执行的摘要和逐文件详情。

## 3. P0：主框架正式模块启动模式

### 当前行为

```text
python -m app
→ app.__main__.main(use_mocks=True)
→ build_context(use_mocks=True)
→ Registry 扫描 mock_modules/
```

真实模块模式下，`build_context` 的 real root 是 `AppPaths.modules`，不是自动等于源码仓库 `modules/`。发布负责人需要决定正式模块的安装目录和切换方式。

### 建议方案

- 增加受支持的 `--real-modules`、配置项或部署模式；
- 正式模式扫描已安装的 real modules 目录；
- UI/诊断页面明确显示 `is_mock`、模块路径和版本；
- 生产构建不得悄悄回退到 Mock；
- Mock 继续用于演示、测试和离线服务模拟。

### 验收标准

- 普通用户能够明确选择或识别正式模式；
- Registry 显示 `module_id=moisture`、`is_mock=false`、版本 `0.1.0`；
- Runner 实际调用 `modules/moisture/run_module.bat`；
- 结果中心能打开正式 XLSX、Markdown 和 result。

## 4. P0：TaskService 快照与历史年份

### 复现

历史 Excel 内只有“4.8”“4.10”等月日，原目录为 `2026年4月份`。GUI 选择文件后：

```text
原始：2026年4月份/4.10某供应方原竹丝水分检测.xlsx
快照：tasks/<job_id>/inputs/001-4.10某供应方原竹丝水分检测.xlsx
```

模块收到快照后无法从内容或快照路径可靠知道年份，返回：

```text
WORKBOOK_PROCESSING_FAILED: WorkbookStructureError
```

这不是用户操作错误，也不应通过当前年份或文件时间猜测。

### 推荐最小修复

使用现有 JobRequest 字段 `module_config_file`，原则上不修改官方 Schema：

1. 任务创建入口允许提供模块配置；
2. `build_draft_job` 不再固定 `module_config_file=None`；
3. 任务目录生成模块配置，例如 `{"default_year": 2026}`；
4. draft 和 finalize 都传递、快照并验证同一配置；
5. 重启恢复时保持配置引用稳定；
6. UI 可提供年份输入，或提供经过校验的模块配置选择入口。

不要让主框架解析水分公式或供应商业务。主框架只负责保留/传递模块配置。

### 必测场景

- GUI → TaskService 快照 → Runner → BAT → 模块成功；
- draft/finalize 使用相同 `default_year`；
- 配置缺失、非法、越界和路径替换被拒绝；
- 完整日期不依赖 default year；
- 原文件 SHA-256 前后不变；
- 重启恢复后仍能 finalize。

## 5. P0：正式模块打包、安装与运行时

### 当前缺口

- PyInstaller spec 只把 `mock_modules/` 加入 portable bundle；
- portable verifier 只要求三个 Mock manifest；
- 主框架根依赖缺少水分模块需要的 `jsonschema`、`XlsxWriter` 和 `Jinja2`；
- 冻结应用只设置 `BAMBOO_MODULE_HOST`，没有向正式模块提供 `BAMBOO_MODULE_PYTHON`；
- 安装后的 `AppPaths.modules` 没有正式模块安装、升级、回滚或完整性校验流程；
- T24 计划中的模块 ZIP 不包含 `.venv`，仅生成 ZIP 并不能证明安装版能够启动模块。

### 负责人必须批准的部署模型

从以下方案中选择并固定一种：

1. 主框架安装包内置正式水分模块和全部运行依赖；
2. 正式模块独立安装到 `AppPaths.modules`，主框架提供受控 Python 运行时；
3. 模块包自带隔离运行环境，并由主框架校验版本、hash 和入口。

无论选择哪种方式，都必须明确：

- Python 版本基线：主框架当前为 3.12，模块声明支持 3.11+；
- 模块依赖由谁安装、更新和扫描；
- 模块 ZIP/SHA-256 如何与安装目录对应；
- 失败升级如何回滚，规则/经验数据如何保留；
- 生产环境不得依赖开发仓库 `.venv` 或系统 PATH。

### 发布验收

- 在无源码仓库、无开发 `.venv` 的干净 Windows 环境安装；
- Registry 发现正式模块且 `is_mock=false`；
- `version`、`self-check` 和真实 Excel 任务均成功；
- 模块依赖不从网络临时安装；
- 卸载、升级和回滚不破坏用户任务历史。

## 6. P0：CI 与正式模块门禁覆盖

当前 `scripts/verify_repo.ps1` 只 lint `app/core/ui/mock_modules/scripts/tests`，默认 pytest 也只覆盖根 `tests/`，合同 CLI 只验证三个 Mock 模块。GitHub quality/package workflow 只安装主框架依赖，因此主框架 CI 可以在完全没有运行正式水分模块测试的情况下通过。

负责人需批准将以下内容加入正式门禁：

- 安装或锁定 `modules/moisture/requirements.txt`；
- 合同 CLI 验证 `modules/moisture`；
- 执行 `modules/moisture/tests`；
- 使用 `use_mocks=false` 的 Registry/Runner/TaskService smoke；
- 打包后从真实模块目录运行 `version/self-check/run`；
- 真实模块失败时阻止 release tag 和安装包发布。

同时应修改本地门禁：仓库 `.venv` 不存在或解释器不属于当前仓库时立即停止，不允许 `verify_repo.ps1` 回退裸 `python`。

## 7. P1：规则批准与颜色

当前规则包：

```text
HIGH_DEFAULT: total_average > 0.55, orange
LOW_DEFAULT:  total_average < 0.47, green
status: pending_confirmation
applicable_materials: [竹丝]
```

负责人必须取得业务书面决策：

- `0.55/0.47` 是否为生产阈值；
- “原竹丝”是否属于规则材料范围；
- 区间值是否需要规则及其阈值；
- 橙/绿初筛与红/蓝 AI 辅助语义是否接受；
- 规则版本、来源、批准人和生效时间。

未批准前不得为了“显示颜色”直接把状态改为 confirmed。规则编辑/发布工具当前不存在，运行时规则包保持只读。

## 8. P1：Knowledge、AI 与真实 API

模块已经能够声明 Knowledge/AI service request，并在 finalize 校验响应，但：

- 主框架当前默认 Provider 是 `MockProvider`；
- 真实 API Key、Provider、网络、重试、审计和用户同意都属于主框架；
- 模块不得接触凭据或直接 import HTTP 客户端；
- denied/error/timeout/非法响应必须保留确定性输出；
- 红蓝只允许由严格匹配且达到置信度门槛的结构化证据产生。

接真实 API 前必须完成安全、脱敏、同意和审计评审。

- 不引入数据库、网络知识库或在线发布服务。

## 10. P1：Knowledge 响应的实际用途

当前模块会生成并在 finalize 重建 Knowledge request，主框架也会返回 Knowledge items；但 finalize 的业务应用分支只处理 AI response。普通 Knowledge 内容不会改变确定性结果，也尚未写入 Markdown、XLSX 或经验引用。

负责人必须选择：

1. 将 Knowledge 内容作为非判定性的报告引用，并保留 namespace、record ID 和来源；
2. 暂时禁用没有消费者的 Knowledge request；
3. 明确未来与本地经验库的优先级和去重规则。

任何 Knowledge 文本都不得升级颜色、覆盖已批准规则或成为正式责任结论。

## 11. P1：输出隐私与分享范围

当前 XLSX“来源追溯”写入完整输入路径、文件 hash、工作表和样本行；汇总表包含供应商和材料信息。这适合本机审计，但文件被邮件、网盘或其他系统转发时可能暴露用户名、目录结构和业务身份。

负责人需与业务/安全负责人批准：

- 正式报告是仅限本地，还是允许对外分享；
- 来源文件字段使用绝对路径、相对路径、文件名还是受控 source ID；
- 供应商身份是否需要脱敏版导出；
- hash 和样本行信息的保留期限；
- 本地任务目录、日志和历史数据库的清理策略。

AI payload 已有独立脱敏边界，但不能替代 artifact 的分享策略。

## 12. P1：错误分类与用户体验

模块当前把单文件异常安全压缩为 `WORKBOOK_PROCESSING_FAILED: <ExceptionType>`，主框架失败弹窗则把所有 `result.errors` 连接成一段文本。批量失败时会形成超长弹窗，并且用户无法区分缺年份、缺表头、样本超限或文件损坏。

建议负责人批准：

- 弹窗只显示任务级摘要和前若干条代表错误；
- 结果中心提供逐文件错误表和可复制详情；
- 模块输出稳定、无敏感信息的错误 code，例如年份缺失、模板不匹配、样本超限；
- stderr/日志保留技术诊断，但 UI 不显示 traceback；
- 相同错误聚合计数并给出可执行修复提示。

## 13. P1：BAT Python 探测与解释器基线

`run_module.bat` 当前使用 `%TEMP%` 下带 `%RANDOM%` 的临时文件验证 Python 哨兵。历史 Gate D 全量运行曾间歇出现临时探测文件占用，单项重跑通过；最近模块全量和仓库门禁均已通过。

若再次出现：

```text
No approved virtual environment provides Python 3.11 or newer and required dependency jsonschema.
```

先确认是否伴随“文件被另一进程占用”。修复必须同时满足：

- 真实验证 Python 3.11+ 和 `jsonschema`；
- 拒绝只返回退出码 0 的伪 Python；
- 不使用共享碰撞临时文件；
- 从仓库外目录启动仍成功；
- 不回退到系统 Python。

主框架声明 Python `>=3.12,<3.13`，模块声明 Python `>=3.11`。负责人需要明确集成发布只支持 3.12，还是继续维护模块独立 3.11 兼容矩阵。

此外，`scripts/verify_repo.ps1` 当前在找不到仓库 `.venv` 时回退裸 `python`，与本项目本地开发约束冲突。该问题和 BAT 临时文件风险属于 T21/T22/发布门禁边界，不要在打包任务中降低校验。

## 16. 经验库交接

只读 repository 只允许返回 `experience/approved/` 中 manifest 登记且有效的经验；当前正式管线尚未自动调用该 repository。离线管理入口：

```powershell
$env:PYTHONPATH = (Resolve-Path "modules\moisture\src").Path
.\.venv\Scripts\python.exe -m moisture.tools.manage_experience --root modules\moisture\experience list
```

管理命令包括 `list/show/validate/create/update/publish/retire`。approved 不可原地修改，修改必须创建新版本；retired 不物理删除。经验内容和证据来源由业务负责人批准。
