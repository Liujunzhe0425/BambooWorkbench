# 小模型任务撰写与执行指导

## 1. 目的

本文件用于在 BambooWorkbench 后续开发中合理分配模型任务、控制 Token 和返工成本。

固定分工原则：

- **Codex**：承担高风险、高耦合、大范围以及需要跨系统判断的任务；
- **Claude Code + DeepSeek API**：承担边界清晰、影响范围小、验收明确的实现和文档任务；
- 小模型完成的内容不因测试通过就自动视为可交付，涉及正式合同、跨模块行为和安全边界时仍需由 Codex 或负责人复核。

目标不是让小模型独立决定架构，而是把已经拆解清楚的工作可靠地执行完。

## 2. 任务分流标准

### 2.1 必须交给 Codex 的任务

满足以下任一条件，原则上不得直接交给小模型：

- 修改 Registry、Runner、TaskService、Bootstrap、官方 Schema 或进程合同；
- 同时修改 `app/`、`core/`、`ui/`、业务模块等多个责任域；
- 涉及 draft/finalize 身份、confirmation、service request/response 的稳定性；
- 涉及真实 Provider、API Key、凭据、网络许可、脱敏或外发数据；
- 涉及数据库迁移、升级兼容、安装包、发布流程或 CI 全仓门禁；
- 涉及路径越界、原子写入、进程隔离、取消、超时等安全问题；
- 故障根因尚不明确，可能存在多个责任层；
- 需要重构架构、修改公共接口或决定长期兼容策略；
- 预计修改超过 8 个文件，或影响多个业务模块；
- 失败可能破坏用户数据、正式成果、历史任务或发布包；
- 需求本身存在冲突，需要作出业务或架构取舍。

### 2.2 适合交给小模型的任务

小模型任务应同时满足大部分条件：

- 目标可以用一两句话准确描述；
- 允许修改的目录和文件能够明确列出；
- 不改变公共 Schema、跨进程合同和架构边界；
- 主要是局部实现、测试补充、文档更新或机械性适配；
- 有现成实现、测试或相邻代码可以模仿；
- 验收命令少而明确，通常为 1—3 条定向测试；
- 出错后可以安全撤销，不影响用户数据；
- 预计修改不超过 5 个文件，最好集中在一个目录；
- 不需要读取整个旧项目或全仓历史；
- 不需要访问真实密钥、客户原始数据或生产服务。

典型任务包括：

- 修正文档、README、命令示例和链接；
- 为已有函数补充一两个边界测试；
- 修正局部 import、类型标注、错误提示或路径引用；
- 按既有模式增加一个明确字段的显示；
- 更新 fixture、脱敏样本或测试期望；
- 修复已定位、责任文件明确的简单缺陷；
- 执行无代码修改的定向验证并整理结果。

### 2.3 不确定时的判断方法

依次询问：

1. 小模型能否只读取少量指定文件就理解任务？
2. 能否明确说出“不允许修改什么”？
3. 能否通过少量定向测试判断完成或失败？
4. 即使实现错误，是否只影响局部且容易恢复？

四项均为“是”时，可以交给小模型。任一项为“否”，先由 Codex分析、拆分或执行。

## 3. 小模型任务必须包含的内容

不要只写“修一下这个问题”。每个任务至少写明以下信息。

### 3.1 背景

用最少文字说明当前行为、期望行为和已知根因。根因不确定时，不应把任务包装成直接修改任务，应先交给 Codex诊断。

### 3.2 单一目标

一次任务只解决一个责任问题。例如：

> 修正 README 中已经失效的水分模块运行命令，使其与当前 `run_module.bat` 用法一致。

不要把“修改文档、修复 Runner、接入 DeepSeek、重新打包”合并为一个小模型任务。

### 3.3 修改范围

明确列出允许修改的文件或目录，例如：

```text
只允许修改：
- modules/moisture/README.md
- modules/moisture/tests/contract/test_cli_health.py
```

同时列出禁止范围，例如：

```text
禁止修改：
- app/
- core/
- ui/
- contracts/
- .github/
- 其他业务模块
```

### 3.4 业务和技术约束

写出不能被“顺手优化”的行为，包括：

- 保持现有算法和结果语义；
- 不修改官方 Schema；
- 不引入网络、Provider、数据库或新依赖；
- 不扩大兼容层；
- 不把失败改成伪成功；
- 不通过降低校验标准让测试通过。

### 3.5 验收标准

验收必须可观察，避免“效果良好”一类模糊描述。例如：

- 指定测试全部通过；
- 相同输入重复执行得到相同 ID；
- `git diff --check` 通过；
- 只出现计划内文件修改；
- README 中的命令可直接复制执行。

### 3.6 停止条件

明确要求小模型在以下情况停止并汇报：

- 需要修改禁止目录；
- 发现需求与现有合同冲突；
- 需要新增依赖或访问网络；
- 同一错误连续两轮修复仍未解决；
- 工作区存在会被覆盖的用户改动；
- 测试失败属于其他责任模块；
- 无法证明修改不会影响正式数据。

## 4. 可复制的小模型任务模板

```markdown
# 任务名称

## 背景

[当前现象、期望行为、已经确认的根因。]

## 本次唯一目标

[用一句话描述必须完成的结果。]

## 开始前只读检查

只读取：
- [文件 1]
- [文件 2]
- [相关测试]

不要遍历旧项目全部历史，不运行全仓测试。

## 允许修改

- [允许目录或文件]

## 禁止修改

- [禁止目录或文件]
- 不修改公共 Schema 和进程合同
- 不新增依赖、Provider、网络或数据库
- 不重构无关代码

## 实现要求

1. [要求 1]
2. [要求 2]
3. [要求 3]

## 环境要求

所有 Python 命令显式使用：

`.\.venv\Scripts\python.exe`

禁止使用裸 `python`、`py`、系统 Python 和全局安装依赖。

开始前验证：

`.\.venv\Scripts\python.exe -c "import sys; print(sys.executable); print(sys.version)"`

如果解释器不属于当前仓库 `.venv`，立即停止。

## 定向测试

只运行：

`.\.venv\Scripts\python.exe -m pytest [指定测试] -q`

然后运行：

`git diff --check`
`git status --short`

## 停止与升级

同一错误最多自主修复两轮。仍失败，停止并汇报：失败命令、退出码、错误摘要、责任范围和最小建议，不扩大修改。

## 完成汇报

只汇报：

| 项目 | 结果 |
| --- | --- |
| 修改文件 | |
| 定向测试 | |
| 未解决问题 | |
| Git 状态 | |

不 push、不合并、不创建 PR，除非任务明确授权。
```

## 5. 小模型执行纪律

小模型收到任务后应遵守以下顺序：

1. 查看 `git status --short`，确认不会覆盖用户改动；
2. 验证仓库 `.venv` 解释器；
3. 只读任务明确指定的代码、测试和文档；
4. 先说明根因与最小修改方案，再开始编辑；
5. 只修改允许范围内的文件；
6. 先运行最小定向测试；
7. 失败时最多进行两轮有依据的修复；
8. 运行 `git diff --check` 和 `git status --short`；
9. 汇报实际结果，不把未运行的测试写成通过；
10. 未经授权不提交、不 push、不创建或合并 PR。

不得使用：

- `git reset --hard`；
- `git clean`；
- 自动 `git stash`；
- `git add -A`；
- 裸 `python`、`py`、`py -3`；
- 全局安装依赖；
- 为通过测试而修改无关 expected；
- 在根因不明时进行大范围搜索替换。

## 6. DeepSeek API 数据安全

Claude Code 接入 DeepSeek API 后，提示词、代码片段和日志可能离开本机处理。向小模型发送内容前必须进行最小化和脱敏。

禁止发送：

- API Key、Token、密码和 Windows 凭据；
- 客户原始 Excel、真实供应商身份和个人信息；
- 完整运行日志中的本机用户名、绝对路径和环境变量；
- 未公开的生产数据、数据库内容和内部凭据配置；
- 与任务无关的大段源码或整个仓库压缩包。

允许优先发送：

- 脱敏 fixture 和合成样本；
- 最小错误堆栈；
- 与问题直接相关的函数和测试；
- 相对路径、接口摘要和 Schema 的必要片段；
- 已确认可以外发的公开文档。

API Key 必须由本机凭据系统或环境注入，不能写入提示词、源码、测试、Job、日志和 Git。

## 7. Codex复核与升级条件

小模型完成后，以下任务必须升级给 Codex复核：

- 改动公共接口、Schema 或跨进程协议；
- 改动超过原任务允许范围；
- 出现跨模块测试失败；
- 涉及真实 AI、知识库、凭据或联网许可；
- 涉及规则/经验发布、回滚和正式版本；
- 涉及安装包、CI、升级或数据迁移；
- 小模型对根因或影响范围表述不确定；
- 定向测试通过但行为与真实主框架运行不一致。

推荐复核材料：

- 原始任务文本；
- `git diff --stat` 和相关 diff；
- 实际执行的测试命令与结果；
- 小模型列出的假设和未解决问题；
- 若涉及界面或成果文件，附脱敏截图。

## 8. Token 使用建议

- 一次只交付一个小任务，避免把多个阶段塞进同一上下文；
- 提供准确文件路径，避免让小模型遍历全仓；
- 提供已确认根因，减少重复诊断；
- 优先迁移现有实现和测试，不要求重新设计；
- 先覆盖代表性正常路径和一个失败路径，再决定是否扩展边界矩阵；
- 每批只做一次较大回归，全仓门禁优先交给 GitHub Actions；
- 不让小模型反复阅读旧项目全部历史；
- 同一错误两轮未解决立即升级，避免无止境消耗额度。

## 9. 示例分流

| 任务 | 建议执行者 | 原因 |
| --- | --- | --- |
| 修正 README 中过期命令 | 小模型 | 文件单一、验收明确 |
| 为现有 Schema 校验补一个非法字段测试 | 小模型 | 局部测试、边界清晰 |
| 根据已定位根因修复一个错误提示 | 小模型 | 风险低、易回退 |
| 将 moisture 正式接入 Registry 并替代 Mock | Codex | 跨 Registry、Runner、UI 和打包 |
| 接入 DeepSeek Provider 和凭据管理 | Codex | 涉及网络、密钥、同意和降级 |
| 修改 draft/finalize ID 生成规则 | Codex | 跨进程身份合同、高风险 |
| CI 中补建仓库 `.venv` | Codex或框架负责人 | 涉及全仓工作流和打包一致性 |
| 更新一份已有交接文档的测试数字 | 小模型 | 纯文档、信息明确 |

## 10. 最终原则

小模型负责“在已确定的边界内准确施工”，Codex负责“识别边界、处理耦合和控制风险”。

如果一个任务需要小模型自行猜测架构、责任人、数据安全策略或兼容方案，说明任务还没有拆解到适合小模型执行的程度，应先交由 Codex分析和切分。
