## 3. 实施顺序

### 阶段 A：建立失败复现和保护测试

先补测试，再修改实现。测试资产全部位于模块目录并使用合成或脱敏数据。

1. 在 `tests/fixtures/workbooks` 补充与历史表同结构的 6 样本和 8 样本工作簿；
2. 构造输入已复制到无年份临时任务目录、`module_config_file=null` 的正式 draft Job；
3. 断言当前问题能够稳定复现为“缺少年份”，而不是其他解析错误；
4. 固化已配置 `default_year=2026` 时的公式、均值、颜色和输入 hash 基线；
5. 增加报告回归断言，捕获错误复核建议、缺失规则上下限和客户不可读枚举。

本阶段只运行最小定向测试，不运行全仓门禁。

### 阶段 B：MOIS-01 缺失年份的一次确认与 finalize 重算

#### B1. 宽容解析，保留确定性数据

- Excel 解析分为“字段/样本提取”和“日期年份补全”两个步骤；
- 缺少年份时继续解析标题、材料、供应商、部门、样本质量、表内含水率和全部公式输入；
- 只有月/日的日期保留原始月日和来源位置，形成结构化 `default_year_required` 业务问题；
- 缺少年份不得把工作簿标为 `WORKBOOK_PROCESSING_FAILED` 或丢弃已经提取的样本；
- 工作簿已有完整年份时直接使用，不产生年份确认；
- 显式完整年份始终优先，批量年份答案只能补全缺失年份，不能覆盖原值；
- 同批出现多个明确且冲突的年份时单独形成冲突问题，不允许用批量年份静默覆盖。

为减少对既有算法的影响，公式、统计和规则仍接收现有领域模型；新增的日期解析问题在进入
确定性管线前后以窄 DTO 传递，不修改公式和统计函数。

#### B2. 每个 draft 只生成一个年份确认

当一个或多个文件需要默认年份时，生成一个 job 级确认项：

```text
field: default_year
blocking: true
batch_applicable: true
rememberable: false
options: []
value: 用户输入的四位年份
```

要求：

- reason 明确列出“有 N 个文件只有月/日，需要同一业务年份”，不暴露绝对路径；
- confirmation ID 基于 draft root job ID、排序后的受影响文件 SHA-256、字段
  `default_year` 和月日摘要生成；
- ID 不使用当前时间、UUID、绝对路径或 finalize job ID；
- 同一输入重复 draft 得到相同 ID；输入内容变化后 ID 必须变化；
- 多文件只显示一个输入框，用户使用批量应用语义一次回答；
- draft 状态为 `needs_confirmation`，受影响文件不得计为结构损坏；
- draft 可以输出明确标注“年份待确认”的临时摘要，但不得冒充正式完成结果。

#### B3. 严格读取年份答案

finalize 对 `default_year` 答案实施严格校验：

- 接受确认页面提交的四位数字字符串，并规范化为整数；
- 合法范围固定为 1900—2100；
- 拒绝布尔值、小数、空值、前后夹杂文字、超范围年份和重复答案；
- 多文件年份确认要求 `apply_to_batch=true`；单文件允许 false；
- confirmation bundle 的 job ID 必须等于 draft root job ID；
- 缺少答案、未知 ID 或答案不完整时 finalize 失败，不猜测当前系统年份；
- 答案只在本次 finalize 内存中使用，不写回原文件、规则包或经验库。

#### B4. 完整重算

finalize 使用 `parent_job_id` 重建 draft 身份，并以年份答案重新执行完整确定性管线：

- 不读取 draft 输出目录；
- 不依赖前一进程内存或隐藏数据库；
- confirmation ID 与 draft 完全一致；
- 重新计算日期、公式、统计、规则、颜色、XLSX 和 Markdown；
- 正式 result 使用 finalize 自身 job ID；
- finalize 的 confirmations 和 service_requests 均为空；
- 21 份历史表应由一次年份回答全部完成。

### 阶段 C：MOIS-02 复核建议一致性

集中建立一个展示文案映射，避免 XLSX、Markdown 和异常明细各自拼接矛盾文字：

| 确定性状态 | 正式业务文案 |
| --- | --- |
| high/orange | 均值高于 0.55，建议复核取样、烘干和称量记录 |
| low/green | 均值低于 0.47，建议复核取样代表性和称量记录 |
| normal/none | 未命中已确认筛查规则 |

文案中的阈值必须来自当前已加载规则快照，不能在 writer 内另写一套业务常量。所有异常文案
继续附带“筛查提示，不是正式不合格或责任结论”的声明。

### 阶段 D：MOIS-03 完整展示规则依据

调整确定性结果到报告 DTO 的映射，使所有 high、low 和 normal 批次都携带当前适用规则包的
上下文，而不是只有命中记录才有阈值。

每个批次在 XLSX 和 Markdown 中至少展示：

- 初筛下限 `0.47`；
- 初筛上限 `0.55`；
- 规则版本 `default-v1-approved`；
- 当前规则文件 SHA-256；
- 适用材料“竹丝/原竹丝”；
- 确认状态 `confirmed`（客户展示为“已确认”）。

实现要求：

- 依据从 `RulePackageSnapshot` 和适用规则定义提取，不从报告模板硬编码；
- normal 批次也展示实际上下限和版本，不再输出“未配置”；
- 若未来确实不存在适用规则，才允许显示“无适用的已确认规则”，不得伪造阈值；
- 追溯页保留机器版本和 hash，业务页使用清晰中文标签。

### 阶段 E：MOIS-04 清理客户可见占位词

在展示边界增加明确的中文映射，不修改机器合同枚举：

| 机器值 | 客户展示 |
| --- | --- |
| `none` | 正常/无颜色 |
| `None` 或空规则 ID | 未命中筛查规则或留空 |
| `not_required` | 无需人工确认 |
| `pending_human_review` | 待人工复核 |
| `not_completed` | 辅助复判未完成 |

对生成后的 XLSX XML 和 Markdown 进行静态断言，确保客户可见区域不出现
`None`、`not_required`、`pending_human_review` 等内部值。`result.json` 和追溯页仍保留合同要求
的机器字段。

### 阶段 F：MOIS-05 文档真实性整改

扫描并修正 `modules/moisture/**/*.md`：

- 删除所有开发机绝对路径，命令统一从仓库根目录使用相对路径；
- 删除已经不存在的旧 Mock 启动参数说明，统一采用当前框架的 `--demo` 语义；
- 删除“任务页已有默认业务年份输入框”的错误描述，改为“一次年份 confirmation”；
- 阈值状态与当前规则包保持一致：`0.47/0.55`、竹丝/原竹丝、`confirmed`；
- 将尚未由负责人复验的正式接入、便携包 EXE、CI 完整通过等表述改为“待验收”或提供实际
  证据后再声明完成；
- 真实 AI、规则治理 UI、经验治理 UI 和 AI 报告增强明确列为后续框架任务；
- 迁移证据中必须提及旧路径时使用 `<旧仓库>` 等脱敏占位，不保留本机绝对路径；
- README 的自测步骤与当前 integration 默认加载真实模块的行为一致。

### 阶段 G：MOIS-06 真实框架与历史数据回归

## 7. 停止条件

出现以下任一情况立即停止，不扩大修改范围：

- 最新 integration 无法干净合入，且冲突要求修改模块外文件；
- 官方合同无法表达年份确认，必须修改 `contracts/`；
- 主框架现有确认页无法提交年份且必须修改 `ui/`；
- 两轮修复后仍无法保持 166 条公式或 21 个均值零差异；
- 需要在模块内硬编码 2026、系统当前年份、真实路径或供应商身份；
- 需要降低 Schema、hash、路径或 finalize 身份校验；
- 需要直接 push/merge `integration` 或 `main`。

停止时只报告复现步骤、失败层、退出码、错误摘要、责任边界和最小修复建议，等待项目或框架
负责人决定。
