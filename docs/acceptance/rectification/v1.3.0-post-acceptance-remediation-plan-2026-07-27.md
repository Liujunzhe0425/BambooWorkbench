# BambooWorkbench v1.3.0 人工验收后整改总计划

日期：2026-07-27

基线：`integration@b89d5f4d6ebcff73f386ed791a7a0cb017bf35ab`

性质：v1.3.0 人工验收后缺陷整改；修复候选版本已批准为 v1.3.1

## 已确认问题

1. 水分任务创建页在小窗或高 DPI 下压缩表单，文字被裁切。
2. 三个模块的正式任务均失败，统一显示 `monthly_rollup module finalize result is missing a snapshot`。
3. 私有 Release 自动更新未配置本机只读令牌；不得把令牌写入源码或安装包。
4. 知识库的确定性检索区域在小窗或高 DPI 下压缩表单。
5. 历史数据页年份上限只有当前年加一，月份卡片没有利用完整空间，模块切换缺少可见高亮；当前无正式月份时月份卡片按设计禁用。

## 四方责任边界

### 框架负责人

负责：

- `ModuleTaskPage`、`KnowledgePage` 的滚动与响应式布局；
- 月度 finalize 结果的状态感知校验，保留模块原始失败原因；
- 历史数据页 2000—2077 年范围、列伸缩、卡片尺寸和模块选中样式；
- 成功任务/月度槽位/结果页接线，以及失败、部分成功、取消任务不误登记正式月份；
- 自动更新凭据的本机安全配置与更新链路验证；
- 框架、UI、安装版和真实模块联合回归。

不负责：

- 修改三个模块的 Excel 解析、业务日期解释、公式、阈值或统计口径；
- 为模块伪造月度快照；
- 把 GitHub Token、API Key 或其他密钥写入仓库、日志、SQLite、安装包或 Release。

### 水分负责人

仅负责 `modules/moisture/` 内真实业务记录 ID 与私有快照 Schema 的一致性、稳定错误码和水分完整链路测试。不得修改框架或其他模块。

### 水煮负责人

仅负责 `modules/boiling/` 内 draft/finalize 确认集合稳定性、成功结果与月度快照的一致性，以及水煮完整链路测试。不得修改框架或其他模块。

### 售后负责人（由水分负责人临时代管）

本轮明确授权水分负责人修改 `modules/after_sales/`。其任务是补充任务年月与业务日期冲突的 draft 人工确认、安全处理零匹配月份，并保持售后业务输出与 AI 边界。该授权不扩展到框架、水煮或其他目录。

## 框架侧整改计划

### 1. 小窗与高 DPI 布局

- 为任务创建页和知识库页增加纵向滚动容器或等价的响应式承载层；
- 保证 980×660 最小窗口和 Windows 125%/150% 缩放下，输入框、下拉框、按钮文字不被裁切；
- 保持最大化时内容正常拉伸，不出现不必要的横向滚动条；
- 不回退已经修复的 AI 配置页面布局。

### 2. 月度快照状态感知

- `success` 且带年月、模块声明月度能力时必须提供合法快照；缺失时仍作为模块合同错误；
- `failed`、`partial_success`、`cancelled` 不因快照为空而覆盖模块原始状态和错误；
- 只有 `success + 合法快照 + 累计事务成功` 才能登记或替换正式月份；
- 模块失败信息必须以稳定、脱敏方式呈现，不能统一覆盖为“缺少快照”；
- 失败候选不得替换旧正式结果、写入学习证据或创建正式月份卡片。

### 3. 历史数据页

- 年份固定支持 2000—2077，默认当前年份；
- 列数变化时清除旧列伸缩权重，禁止出现占宽的空列；
- 月份卡片横向填满当前网格列，并保持清晰、稳定的最小高度；
- 为三个模块切换按钮增加明确的 checked/选中视觉样式；
- “未创建”月份继续禁用且不显示“不可点击”；已创建月份可打开对应完整结果。

### 4. 自动更新凭据

- 不从 GitHub CLI 静默复制高权限令牌，不内置任何令牌；
- 团队测试只接受该仓库 `Contents: read` 的细粒度令牌，并保存到 Windows 凭据管理器的 `BambooWorkbench / github-updates`；
- 令牌由用户另行提供或在设置页输入后，再验证私有 Release 检查和下载；
- 客户分发继续以独立公开二进制源或 HTTPS/CDN 为目标方案。

## 分支与交付顺序

1. 四方可并行在各自分支开发，但都从最新 `integration` 开始。
2. 框架修复使用独立 `agent/...` 分支，PR 目标为 `integration`。
3. 三个模块分别从既定 module 分支创建新的 Draft PR：
   - `module/moisture-test → integration`
   - `module/boiling → integration`
   - `module/after-sales → integration`
4. 已合并的旧 PR #63/#65/#67 不得作为本轮交付；本轮必须提供新的 PR 编号。
5. 框架公共修复先验收并进入 integration 后，三个模块在最终交付前再次同步最新 integration，运行正式链路测试。
6. 四项 PR 全部通过联合验收后，只有得到用户明确授权才能继续 `integration → main`、更新中央版本、打标签、打包或发布 Release。

三个模块在各自整改 PR 中把模块版本和模块 CHANGELOG 更新到 `1.3.1`。框架中央 `app/pyproject/installer` 版本元数据在四方联合验收通过后的统一 release 准备提交中更新，避免未验收代码提前成为正式版本。

## 联合验收门槛

- 三模块合同 CLI、BAT version/self-check、draft → confirmation → finalize → snapshot → rollup 全部通过；
- 水分真实中文/Unicode 业务 ID 可以生成快照；
- 水煮 finalize 不产生 draft 中不存在的新阻断确认，成功必有快照；
- 售后年月冲突在 draft 阶段明确呈现，零匹配月份不进入正式成果事务；
- 三个模块失败时框架显示各自稳定原因，不再统一显示缺少快照；
- 历史页已创建月份可点击，模块切换有高亮，年份包含 2077；
- 980×660 与默认 1180×760 下任务页和知识库页控件不裁切；
- Ruff、完整框架测试、完整模块测试、便携运行时、安装版 smoke、`git diff --check` 通过；
- 不提交客户原始 Excel、任务目录、绝对路径、密钥或真实客户数据。

## 当前禁止事项

- 不在联合验收前修改中央正式版本号，不创建标签或 Release；模块内部版本按已批准目标更新为 `1.3.1`；
- 不直接提交 main 或 integration；
- 不把 GitHub Token 或 API Key 写入安装包；
- 不通过放宽路径、哈希、Schema 或快照真实性校验来让测试“通过”；
- 不因模块负责人新增合理的模块内部改进而一律打回，但任何公共接口变化必须提交独立 FCR。
