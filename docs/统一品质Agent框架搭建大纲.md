# BambooWorkbench（竹简工作台）统一品质数据处理 Agent 框架搭建大纲

统一命名：产品英文名、项目总文件夹名和GitHub仓库名均为`BambooWorkbench`；中文产品名为“竹简工作台”。

## 1. 建设目标

搭建一个统一入口的品质数据处理 Agent。客户只启动一个工具，即可在以下三种业务模式间切换：

1. 原竹丝水分检测；
2. 水煮实验；
3. 售后统计。

统一框架负责接收文件、识别或选择模块、创建任务、调用模块、展示待确认事项、管理输出和记录日志。三个业务模块负责各自的字段提取、公式复核、规则判定、异常识别、图表和分析报告。

第一版的重点是减少人工重复录入和汇总，不替代品质人员完成放行、责任认定、赔偿、关闭确认等高风险决策。

## 2. 第一版范围

### 2.1 必须实现

- 一个统一启动入口；
- 三种业务模式选择，支持后续增加模块；
- 单文件、批量文件和指定文件夹输入；
- 模块自动识别，识别不确定时允许人工选择；
- 临时文件、重复文件和已处理文件过滤；
- 统一任务状态和处理进度；
- 统一展示异常、缺失字段和待人工确认事项；
- 统一输出 Excel、图表、分析报告、异常清单和运行日志；
- 所有结果保留来源文件及追溯信息；
- 单个文件失败不影响同批次其他文件；
- 三个业务模块可独立安装、升级和替换。

### 2.2 第一版暂不实现

- 复杂账号和多级权限系统；
- 云端多租户服务；
- 自动作出产品放行、责任划分或赔偿决策；
- 三类数据之间的自动因果推断；
- 未经客户确认的规则自动学习和永久写入；
- 大规模数据库和企业系统深度集成。

## 3. 总体分层

```text
统一品质数据处理 Agent
├─ 交互层
│  ├─ 首页和模式选择
│  ├─ 文件/文件夹选择
│  ├─ 任务进度
│  ├─ 待确认事项
│  └─ 结果预览与导出
├─ 框架核心层
│  ├─ 模块注册与路由
│  ├─ 任务管理
│  ├─ 文件指纹与去重
│  ├─ 配置与规则版本
│  ├─ 模块进程调用
│  ├─ 结果校验
│  ├─ 日志与审计
│  └─ 输出目录管理
├─ 业务模块层

   ├─ 分析报告
   └─ 历史任务记录
```

## 4. 推荐调用方式

三个模块必须以“自包含模块包”交付，并提供统一命令行入口：

```text
<模块启动命令> run --job <任务JSON路径>
```

框架为每次运行生成 `job.json`。模块读取任务后，在指定输出目录写入 `result.json`、Excel、图表和报告。框架只依赖统一协议，不直接读取模块内部变量。

推荐使用 Python 实现。若模块采用其他语言，也必须提供可以由 Windows 命令行无交互调用的启动命令，并完全遵守相同 JSON 协议。

若三个模块均为 Python，可额外提供 Python 函数接口以提高性能，但命令行接口仍然必须保留，作为稳定的集成边界和故障隔离手段。

## 5. 统一处理流程

```text
用户选择文件或监控文件夹
→ 框架识别新增文件并去重
→ 自动识别模块或由用户选择
→ 框架生成 job.json
→ 调用对应模块
→ 模块提取、计算、校验和分析
→ 模块生成 result.json 和成果文件
→ 框架校验返回结构
→ 用户只处理异常和待确认事项
→ 确认后生成或更新正式成果
```

## 6. 客户人工输入边界

### 6.1 首次配置

- 三类输入文件夹；
- 输出文件夹；
- 水分阈值及适用对象；
- 水煮产品用途与标准映射；
- 异常颜色和等级；
- 售后品牌、问题类型、责任部门；
- 售后费用纳入口径；
- 售后关闭条件。

### 6.2 日常运行

正常情况下，客户只需放入文件并处理待确认事项。Excel中已经存在的数据不得要求客户重复录入。

### 6.3 必须人工确认

- 原文件缺失且无法可靠推断的关键字段；
- 产品用途或标准版本；
- 数值复核与人工结论冲突；
- 浸渍剥离等非数值外观判断；
- 售后多问题分类、实际费用、责任和关闭状态；
- 放行、返工、赔偿等权限性决定。

## 7. 框架核心组件

### 7.1 模块注册器

读取每个模块的 `module.json`，获得模块编号、版本、启动命令、支持的文件类型和健康检查命令。新增模块时不修改框架核心业务代码，只增加注册信息。

### 7.2 文件与任务管理器

- 生成任务编号；
- 计算文件指纹；
- 过滤 `~$` 临时文件；
- 防止同一文件重复统计；
- 记录输入、输出、开始时间、完成时间和处理状态；
- 支持单文件失败后的继续处理。

### 7.3 配置和规则管理器

业务阈值、分类词典和标准映射必须放在可维护的 JSON/YAML 配置中，不得散落硬编码在程序中。每次结果记录所使用的规则版本。

### 7.4 模块调用器

以独立进程调用模块，传入任务JSON路径，捕获退出码、标准输出、错误输出和超时。模块依赖冲突时可使用独立虚拟环境，不影响框架和其他模块。

### 7.5 结果校验器

检查 `result.json` 是否符合统一协议，来源文件是否存在、输出文件是否生成、状态和异常等级是否合法。协议不合格的模块结果不得直接展示为成功。

### 7.6 人工确认中心

统一展示：

- 信息缺失；
- 规则冲突；
- 低置信度分类；
- 必须由人员负责的结论；
- 处理失败文件。

支持接受建议、修改、批量应用、保存为后续映射规则，但新规则必须有操作者和时间记录。

### 7.7 输出与审计

统一管理任务输出目录、文件命名和运行日志。每个异常、建议和汇总数字都应能够追溯到来源文件，必要时记录来源工作表和单元格位置。

## 8. 建设阶段

### 阶段A：协议冻结

- 确认模块交接说明；
- 确认 `job.json` 和 `result.json` 字段；
- 确认模块包目录；
- 确认错误码、状态和异常等级；
- 三名模块负责人书面确认。

退出条件：三名负责人均能用自己的模块场景解释如何接收任务和返回结果。

### 阶段B：空框架

- 建立统一启动入口；
- 建立模块注册器；
- 建立任务目录和日志；
- 使用三个模拟模块返回假数据；
- 验证三种模式可以切换。

退出条件：统一框架能够调用三个模拟模块并展示统一结果。

### 阶段C：模块独立接入

- 按交付清单逐个验收模块；
- 先运行模块自检；
- 再用统一框架调用；
- 核对历史样本和预期结果；
- 登记接口问题和业务问题。

退出条件：每个模块单独接入后均可完成输入到输出的闭环。

### 阶段D：统一体验

- 统一页面和操作流程；
- 统一任务状态、异常等级和提示文案；
- 统一输出目录和文件命名；
- 统一人工确认方式；
- 验证模块故障隔离。

退出条件：客户无需学习三套不同操作方式。

### 阶段E：客户验收

- 客户分别运行三个模式；
- 使用未参与开发的新文件验证；
- 记录误报、漏报和交互问题；
- 完成整改和回归测试；
- 形成使用说明、验收记录和已知限制。

退出条件：严重问题为零，客户能够独立操作并同意进入试用。

## 9. 框架成功标准

- 一个入口可稳定调用三个模块；
- 模块可以独立替换和升级；
- 正常文件无需重复手工录入；
- 只向客户展示必要的异常和确认项；
- 原文件不被修改；
- 重复运行不重复统计；
- 单个模块或单个文件失败不拖垮其他任务；
- 核心计算、汇总和来源追溯准确；
- 所有高风险业务结论保留人工确认；
- 新增第四个模块时无需重写框架核心。
