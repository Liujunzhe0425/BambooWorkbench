# 竹简工作台三个业务模块最终交接说明

> 发送对象：竹丝水分、水煮实验、售后分析三位模块负责人
>
> 适用基线：`BambooWorkbench v1.0.0` 正式集成版；三个模块的正式版本均统一为 `1.0.0`
>
> 核心原则：每人交付一个独立可验证的业务模块，不修改框架代码，不单独制作桌面界面。

> 版本说明：v1.0.0 发布后，水分原 `0.1.2`、水煮原 `0.2.2`、售后原 `1.4.0` 均以 `1.0.0` 作为新的共同正式基线。该调整不代表功能回退；后续更新必须先同步最新 `integration`，再从 `1.0.1` 或 `1.1.0` 继续递增。

> 界面基线：框架已统一使用深竹绿侧栏、浅色卡片工作区和 `logo/team-logo.png`。模块负责人不得替换 Logo、主题、标题栏、导航或另建 GUI；模块接入后会自动出现在统一工作台入口中。

## 1. 你需要完成什么

框架已经负责统一界面、文件选择、任务进度、本地存储、历史记录、人工确认、AI 授权、知识检索、结果展示和故障隔离。你只负责自己模块内的业务处理：

1. 从历史 Excel 和新输入中提取字段；
2. 按已确认的公式、标准、规则和经验计算与判定；
3. 标记异常，保留数据来源与规则编号；
4. 仅对缺失、冲突、低置信度或权限性结论提出人工确认；
5. 生成汇总 Excel、图表和分析报告；
6. 通过统一 JSON 协议把结果返回竹简工作台。

你交付的是“处理引擎 + 规则知识 + 输出模板 + 测试证据”，不是一套独立软件。框架负责人接入时只应注册模块包，不应复制粘贴业务代码到 `app/`、`core/` 或 `ui/`。

不接受只有界面、只有聊天记录、只有零散脚本，或必须在开发者电脑上人工改路径才能运行的交付。

## 2. 三人的唯一身份与交付位置

| 业务 | `module_id` | 只能使用的分支 | 只能修改的主目录 | 交付 ZIP |
|---|---|---|---|---|
| 竹丝水分检测 | `moisture` | `module/moisture` | `modules/moisture/` | `moisture-<version>.zip` |
| 水煮实验 | `boiling` | `module/boiling` | `modules/boiling/` | `boiling-<version>.zip` |
| 售后分析 | `after_sales` | `module/after-sales` | `modules/after_sales/` | `after_sales-<version>.zip` |

三个分支都由框架负责人从同一个稳定框架提交创建。不要从其他组员的分支分叉，不要直接向 `main` 或 `integration` 推送业务代码。

## 3. 每个模块的业务最低目标

### 3.1 竹丝水分 `moisture`

- 识别供应商、到货/检测日期、总重、取样部门；
- 提取初始质量、烘干质量、锡纸质量；
- 计算并复核单样含水率、部门平均值、总平均值；
- 兼容二厂、品质各 3 或 4 个样品，批量汇总并按日期排序；
- 按可配置规则标记异常，生成汇总表、趋势图和复核建议；
- 忽略 Excel 临时文件，识别重复文件，不对异常原因直接下定论。

最低样本：正常、高值、低值、6 样品、缺字段、重复文件。

### 3.2 水煮实验 `boiling`

- 提取产品、规格、压制日期、班长、检测日期、浸胶日期和订单信息；
- 复核平均厚度、体积、密度、密度差和膨胀率；
- 提取浸渍剥离合格/不合格结论，兼容不同试件数和表格结构；
- 区分正常、异常、信息不足和待确认；
- 原表结论与规则冲突时保留两者并提示复核；
- 产品用途缺失时不得擅自选择膨胀率标准；
- 空表、未完成表不进入正常统计。

最低样本：全合格、密度异常、膨胀率异常、浸渍剥离异常、复测、不同试件数、空表/未完成表。

### 3.3 售后分析 `after_sales`

- 识别不同售后模板和同义字段；
- 提取客户、地点、销售、产品、规格、订单、日期和反馈；
- 提取调查、方案、费用、责任、审批和关闭信息；
- 推荐品牌、性能、外观、加工等问题类型，支持一案多问题与人工修正；
- 区分实际、预估、申请和不纳入统计的费用；
- 责任与关闭状态不明时必须人工确认；
- 生成月/年度汇总、品牌占比、问题占比、责任费用和关闭统计。

最低样本：标准模板、同义字段、多费用、多问题、多责任、未关闭、缺字段、重复文件。

ZIP 解压后顶层必须直接是上述内容，不能再多套一层同名文件夹。依赖、规则、模板和测试数据必须随包交付。

## 5. 不可自行更改的框架合同

机器合同的唯一真实来源是：

- [`contracts/schemas/module-manifest.schema.json`](../../contracts/schemas/module-manifest.schema.json)
- [`contracts/schemas/job-request.schema.json`](../../contracts/schemas/job-request.schema.json)
- [`contracts/schemas/module-result.schema.json`](../../contracts/schemas/module-result.schema.json)
- [`contracts/examples/`](../../contracts/examples/)

`module.json` 不允许额外字段；不要添加 `healthcheck_command`。入口脚本必须支持：

```powershell
modules\<module_id>\run_module.bat version
modules\<module_id>\run_module.bat self-check
modules\<module_id>\run_module.bat run --job D:\absolute\path\job.json
```

退出码固定为：`0` 已生成合法协议结果，`2` 任务输入不合法，`3` 运行失败，`4` 依赖或环境缺失。标准输出只能逐行输出 JSON 进度，诊断文字写入标准错误。

`build_portable_runtime.ps1` 是安装版构建钩子。框架生成
`dist/BambooWorkbench` 后会自动调用它；钩子必须把模块的独立运行时安装进已复制的
`dist/BambooWorkbench/modules/<module_id>/`，并保证在未安装 Python、未激活虚拟环境、
未设置开发环境变量的 Windows 电脑上，入口脚本的 `version`、`self-check` 和
`run --job` 仍可使用。不得把仓库 `.venv`、开发机绝对路径或系统 Python 当成正式运行时。

## 6. draft → 人工/公共服务 → finalize

模块第一次以 `phase=draft` 运行，输出草稿 `result.json`。若有缺失、冲突或权限性结论，在 `confirmations` 中返回；若需要框架知识库或 AI，在 `service_requests` 中返回。

框架收集确认答案、执行允许的服务请求，再以 `phase=finalize` 调用模块。模块必须从 `confirmation_file` 和 `service_response_file` 读取结果，不得猜测路径。

AI 被用户拒绝、无密钥或无网络都是正常状态；模块必须继续生成不依赖 AI 的本地结果。服务请求只能出现在草稿阶段。

## 7. 人工输入要尽量少

框架已能让用户选择单文件或批量文件。模块应自动读取原表、复用已确认规则，不要让用户重复抄写 Excel 里已有的值。只有以下情况才允许进入人工确认：

- 关键字段真实缺失；
- 多个数据源相互冲突；
- 自动映射/分类置信度低；
- 客户尚未确认标准或适用范围；
- 放行、责任、赔偿、审批、结案等必须由人承担责任的结论。

每个确认项必须说明原因、来源、候选值、置信度、是否阻塞、是否可批量应用、是否允许记住映射。

## 8. 代码与数据边界

模块可以读取 `job.json` 明确列出的输入副本、自己的配置/规则/模板，只能向指定 `output_dir` 写入成果。

模块不得：

- 修改 `app/`、`core/`、`ui/`、`contracts/`、`.github/` 或其他模块；
- 直连框架 SQLite，读取 Windows 凭据或 API 密钥；
- 修改、删除或重命名原始 Excel；
- 扫描用户磁盘、访问未授权路径；
- 绕过 `service_requests` 自行调用框架 AI/知识库；
- 硬编码开发者电脑路径、客户身份、账号或密钥；
- 用独立 GUI 或弹窗代替命令行协议。

## 9. 规则必须分层并可追溯

将所有业务知识分为四类：

1. **明确公式**：可自动执行和复算；
2. **已确认标准/阈值**：可自动比较，但必须可配置；
3. **经验建议**：只用于解释与复核提示，不冒充正式判定；
4. **权限性结论**：必须人工确认。

每条公式、阈值、分类映射都要有规则编号、版本、适用范围、来源和客户确认状态。未确认内容要明确标注“待客户确认”。

## 10. 交付前必须通过的测试

除本模块正常样本外，至少覆盖：

1. 单文件、批量、部分成功；
2. 关键字段缺失、规则冲突、人工确认；
3. 错误扩展名、损坏 Excel、空文件、表格格式变化；
4. 非法 JSON、恶意路径、超时、取消和子进程退出；
5. `draft` 到 `finalize` 的完整闭环；
6. 拒绝 AI 后仍可完成本地结果；
7. 原文件处理前后 SHA-256 不变；
8. 同一输入重复运行不会重复统计；
9. 每个脱敏样本都有可机读的预期结果；
10. 核心字段、公式、阈值和标准样本 100% 符合负责人提供的预期结果。
11. 便携包在清空 Python/虚拟环境相关变量后通过 `version`、`self-check` 和至少一次端到端任务。

提交前在仓库根目录运行：

```powershell
python -m app.tools.module_contract_cli validate modules/<module_id>
python -m pytest modules/<module_id>/tests -q
powershell -ExecutionPolicy Bypass -File scripts/verify_repo.ps1
```

## 11. 最终必须交付的东西

一次正式交付必须同时包含：

- 本人 `module/*` 分支的提交号和 Pull Request（目标为 `integration`）；
- 可重复执行的 `build_portable_runtime.ps1` 和无 Python 环境验收证据；
- `<module_id>-<version>.zip`；
- ZIP 的 SHA-256 值；
- 完整源代码、规则、模板和依赖清单；
- 脱敏输入、机读预期结果、实际示例输出；
- 自动测试和完整测试日志；
- 成功、异常、人工确认三类截图；
- 字段/数据源、公式、判定规则、经验/案例、人工权限边界、已知限制文档；
- 待客户确认的规则清单。

框架负责人收到后，应能在不修改模块源码、不安装单独界面、不填写开发者绝对路径的情况下完成：合同校验 → 模块注册 → 模拟/脱敏样本运行 → 人工确认闭环 → 结果文件打开 → 历史记录追溯。任一步需要临时手改框架，均视为未达到最终交接标准。

## 12. 脱敏和禁止上传内容

样本中使用虚构客户、订单、电话、地址和人员；同时移除 Excel 元数据、隐藏表、批注、外链和历史作者。禁止提交企业真实原表、运行日志、SQLite 数据库、`.env`、密钥、API 原始响应或个人凭据。

## 13. 我方后续的接收方式

三位负责人完成后，先由框架负责人按 [`module-acceptance-checklist.md`](module-acceptance-checklist.md) 逐个验收交付包。验收通过后，再将对应分支/提交号、ZIP、SHA-256、测试证据和待确认规则一起交给后续框架接入工作。

当前阶段只交付空框架，不在框架中预先代写三个模块的业务算法。合同验收通过仅证明模块“能被框架安全调用”，业务计算正确性仍必须由模块负责人和客户另行确认。

更完整的字段解释、JSON 示例和调试命令见 [`module-development-guide.md`](module-development-guide.md)。
