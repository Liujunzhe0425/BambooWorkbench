# 三个业务模块后续更新与兼容接入验收说明

> 发送对象：竹丝水分检测、水煮实验、售后分析三位模块负责人
>
> 适用阶段：三个模块已经接入竹简工作台后的所有后续更新
>
> 长期分支：`module/moisture`、`module/boiling`、`module/after-sales`

## 一、先明确责任边界

后续每次更新分为两类责任，不能混在一起：

| 事项 | 责任人 |
|---|---|
| 公式、阈值、分类、统计口径、异常判定是否正确 | 对应模块负责人 |
| Excel、图表、报告、分析建议等业务输出是否正确 | 对应模块负责人 |
| 测试样本和预期结果是否代表真实业务要求 | 对应模块负责人 |
| 模块能否被竹简工作台发现、启动、调用和打包 | 框架负责人 |
| 模块是否遵守统一 JSON 合同和人工确认流程 | 框架负责人 |
| 新模块是否破坏工作台、任务历史或另外两个模块 | 框架负责人 |
| 安装包是否能够携带新模块并在无 Python 环境运行 | 框架负责人 |

框架方后续只进行“兼容接入验收”，不重新判断模块业务计算与输出是否正确。兼容验收通过只表示模块可以继续安装、调用和运行在竹简工作台中，不代表框架方替模块负责人确认了业务结果。

## 二、模块负责人每次更新前要做什么

### 1. 同步最新接入基线

在自己的长期模块分支上同步最新 `integration`，先处理代码冲突，再开始更新。不要从 `main`、其他组员分支或旧的临时分支重新复制一套模块。

```powershell
git fetch origin
git switch module/<自己的分支>
git merge origin/integration
```

如同步时出现框架文件冲突，不要猜测或擅自覆盖，应先通知框架负责人。

### 2. 严格限制修改范围

正常更新只能修改本人目录：

| 模块 | 允许修改的主目录 |
|---|---|
| 竹丝水分检测 | `modules/moisture/` |
| 水煮实验 | `modules/boiling/` |
| 售后分析 | `modules/after_sales/` |

不得顺手修改 `app/`、`core/`、`ui/`、`contracts/`、`packaging/`、`.github/` 或其他组员模块。

如果新功能确实需要框架增加页面、按钮、字段、公共服务，改变合同、接口、任务流程、存储、打包方式或进行其他复杂适配，必须按下一节提交独立的“框架适配请求”。不要把框架代码混进普通模块更新 PR。

### 3. 需要框架适配时，必须提交标准请求文档

只要本次更新不能在现有公开合同内独立完成，就必须新增或更新一份框架适配请求。适用场景包括但不限于：

- 工作台需要增加页面、按钮、表单、筛选器、预览区或结果展示组件；
- `module.json`、任务 JSON、结果 JSON、人工确认或服务请求合同需要变化；
- 需要框架新增 AI、知识库、数据库、任务历史、权限或文件服务；
- 需要调整安装器、便携运行时、模块发现或启动机制；
- 需要跨模块协作、共享数据或复杂工作流；
- 现有接口虽然能够勉强绕过，但会造成重复数据、错误责任边界或明显维护风险。

请求文档必须放在本人模块内的固定目录：

```text
modules/<module_id>/docs/framework-change-requests/
```

每项独立请求使用一个文件，命名为：

```text
FCR-<module_id>-<YYYYMMDD>-<short-name>.md
```

例如：

```text
modules/moisture/docs/framework-change-requests/
  FCR-moisture-20260721-batch-filter-page.md
```

可以复制仓库中的
[`框架适配请求模板.md`](templates/框架适配请求模板.md)。请求至少必须说明：

1. 请求编号、模块、模块版本、负责人和状态；
2. 业务目标和实际使用场景；
3. 现有框架/接口为什么不能满足；
4. 希望框架具体增加或修改什么；
5. 页面、按钮、交互或接口的输入、输出和状态；
6. 是否改变现有合同，是否兼容旧版本模块；
7. 数据安全、人工确认、失败和回滚边界；
8. 可操作、可复验的验收标准；
9. 模块方已经完成的内容，以及等待框架提供的内容；
10. 如果请求未实现，模块是否可以降级运行。

不要只写“请帮我适配”“需要加个页面”或在聊天中口头说明。缺少固定位置的请求文档时，框架方不会猜测需求，也不会直接改框架。

框架方会自动检索本次 PR 中新增或修改的：

```text
modules/<module_id>/docs/framework-change-requests/*.md
```

读取后给出“批准 / 退回补充 / 不属于框架责任 / 暂不采纳”的审核结论。请求合理且信息完整时，由框架方通过独立框架分支实施和测试；完成后将最新 `integration` 同步回模块分支，再继续本模块兼容验收。框架改动不会直接混入组员的业务模块 PR。

如果代码差异已经显示需要框架改动，但负责人没有提交请求文档，本次兼容验收将暂停并要求补交。

### 4. 更新模块版本和记录

每次正式交付至少更新：

- `module.json` 中的模块版本；
- 模块 `CHANGELOG.md`；
- 新增或变化的依赖、规则、模板和说明；
- 与变更对应的测试和脱敏样本。

版本建议：

- 只修复模块内部错误：补丁版本，例如 `1.2.0 → 1.2.1`；
- 增加向后兼容能力：次版本，例如 `1.2.1 → 1.3.0`；
- 改变公共接口或存在不兼容行为：必须提前通知框架负责人，不得直接提交普通更新。

### 5. 模块负责人自行完成业务正确性测试

负责人必须自行确认：

- 公式、阈值、统计口径和人工判断边界正确；
- Excel、图表、报告和建议符合本模块目标；
- 新旧样本的期望结果正确；
- 修复没有破坏以前已经确认的业务行为；
- 客户数据和测试材料已经脱敏。

应随 PR 提供测试命令、结果摘要、脱敏输入和可机读预期结果。框架方只确认这些证据存在且能够执行，不替负责人复算或签署业务结论。

### 6. 完成本模块的接入自检

至少运行：

```powershell
python -m app.tools.module_contract_cli validate modules/<module_id>
python -m pytest modules/<module_id>/tests -q
modules\<module_id>\run_module.bat version
modules\<module_id>\run_module.bat self-check
```

还应完成至少一次 `draft → 人工确认/服务响应 → finalize` 任务，并确认 `build_portable_runtime.ps1` 构建后的模块在未安装 Python、未激活 `.venv` 的环境中可运行。

## 三、如何重新交付

### 1. 推送到本人长期分支

```powershell
git status
git add modules/<module_id>/
git commit -m "module(<module_id>): update to <版本号>"
git push origin module/<自己的分支>
```

提交前再次执行 `git status` 和 `git diff --name-only origin/integration...HEAD`，确认没有修改框架或其他模块。

### 2. 创建指向 integration 的 Pull Request

必须满足：

- 来源：本人长期模块分支；
- 目标：`integration`；
- 不得指向 `main`；
- 不得自行合并；
- 等待框架负责人完成兼容接入验收。

PR 标题建议：

```text
module(<module_id>): update to <版本号>
```

### 3. 向项目负责人发送交付通知

直接复制下面模板填写：

```text
模块名称：
module_id：
模块负责人：
新版本号：
分支：
最新提交号：
PR 链接（目标必须为 integration）：

本次修改内容：
修改文件范围：
是否改变公共接口/合同：否 / 是（如是，附框架变更需求）
是否需要新增框架页面或公共服务：否 / 是（附说明）
框架适配请求文件：无 / modules/<module_id>/docs/framework-change-requests/<文件名>.md

业务正确性自测结论：通过 / 未通过
业务测试命令与结果摘要：
脱敏样本和预期结果位置：
已知限制：

合同校验结果：
version / self-check 结果：
draft → finalize 结果：
无 Python 便携运行结果：
回滚提交或上一稳定版本：
```

信息不完整时，框架负责人可以暂停兼容验收，但不会代替模块负责人补做业务正确性结论。

## 四、收到更新后框架负责人会做什么

模块负责人通知完成后，项目负责人将 PR 链接交给 Codex。后续固定执行以下兼容接入验收：

1. 确认 PR 目标是 `integration`，记录模块版本、提交号和变更范围；
2. 检查是否只修改本人模块目录，是否夹带框架、工作流或其他模块改动；
3. 自动检索 `docs/framework-change-requests/*.md`，并核对代码变化是否还隐含未申报的框架需求；
4. 审核适配请求是否合理、是否属于框架责任、能否复用现有接口、是否保持向后兼容；
5. 校验 `module.json`、统一 JSON Schema、退出码和标准输出协议；
6. 验证 `version`、`self-check`、`run --job`、`draft/finalize` 与人工确认传递；
7. 验证模块可被正式模式发现、注册和启动，Mock 与真实模块不会混用；
8. 验证便携运行时和安装包能够携带该模块，在无 Python 开发环境下可启动；
9. 验证模块失败时不会拖垮工作台，任务历史、输出目录和数据边界仍正常；
10. 运行框架回归和另外两个模块的兼容回归；
11. 检查 GitHub CI 状态，给出“兼容通过 / 兼容不通过 / 需要单独框架变更”的结论；
12. 兼容通过后才允许进入 `integration`，是否进入 `main` 和是否发布新安装包由项目负责人另行决定。

框架方不会在这一步重新计算业务结果、重新定义阈值、评价分析建议是否专业，或对模块负责人给出的预期 Excel 进行业务签字。发现疑似业务结果问题时，只记录并退回对应负责人判断，不修改其业务代码。

## 五、哪些情况会被判定为兼容不通过

- PR 指向 `main`，或直接提交到 `main`/`integration`；
- 修改了本人模块目录以外的文件且没有单独框架变更说明；
- 模块合同、清单、退出码或 JSON 输出不合法；
- 工作台无法发现、启动或完成模块任务；
- 只能依赖开发者电脑的 `.venv`、绝对路径或系统 Python；
- 新模块导致工作台崩溃、历史记录损坏或其他模块不可用；
- 安装包缺失模块运行时或启动时出现终端黑框；
- 负责人没有提供版本、提交号、PR、业务自测结论或回滚依据；
- 公共接口已经改变，却仍按普通内部更新交付。
- 代码明显要求框架新增页面、按钮、接口或复杂适配，但没有在规定目录提交框架适配请求；
- 框架适配请求缺少使用场景、接口/交互说明、兼容性和可复验验收标准。

业务测试不通过属于模块负责人自己的交付未完成；框架方会暂停兼容接入，但不会接管业务修复责任。

## 六、本地和安装版不会自动更新

组员把代码推送到 GitHub 后：

- 项目负责人的本地源代码不会自动变化，必须执行 `git fetch`/`git pull` 或切换到对应提交；
- 已安装的竹简工作台不会自动变化；
- 开发阶段可以拉取 PR 后从源码进行兼容测试；
- 要在正式安装版中测试或交付，必须在合并、验收后重新构建新安装包，并安装新版本；
- 未经兼容验收的模块代码不得直接打包给客户。

## 七、后续固定结论格式

每次兼容接入验收只给出以下三种结论之一：

1. **兼容通过**：可以进入 `integration`；本结论不证明业务输出正确。
2. **兼容不通过**：列明合同、运行时、打包或框架回归问题，由责任方整改。
3. **需要框架变更**：模块需求超出现有公共接口，先独立确认和实现框架变更，再重新验收。

此规则适用于三个模块的所有后续迭代，除非项目负责人明确书面修改责任边界。
