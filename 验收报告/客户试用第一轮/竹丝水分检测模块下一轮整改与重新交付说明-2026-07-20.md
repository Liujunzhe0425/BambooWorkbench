对象：竹丝水分检测模块负责人  
分支：`module/moisture`  
目录：`modules/moisture/`

## 一、本轮责任结论

| 问题 | 责任方 |
|---|---|
| “应用到本批次”勾选框不可见、缺少解释 | 框架方，模块负责人无需修改 |
| Markdown 分析报告无法打开 | 框架方，模块负责人只需继续保证文件和合同声明有效 |
| 输出 Excel 与杨总给定表格不同、结果与预期差异较大 | 竹丝水分模块负责人 |

框架不会修改模块生成的 Excel 内容，也不会替模块负责人判断业务输出正确性。

## 二、必须整改：对齐杨总目标表

### 1. 先建立唯一验收基准

当前仓库没有能够明确识别为“杨总目标汇总表”的黄金样本。负责人必须取得客户确认的目标文件和版本，完成脱敏后将可公开的结构化验收样本放入：

```text
modules/moisture/tests/fixtures/acceptance/customer_expected/
```

若原文件不能进入仓库，应提交：

- 脱敏但保持工作表、列、公式、格式和图表结构的黄金文件；
- 原文件 SHA-256 和保管位置说明，但不得提交客户敏感原件；
- 原文件字段到脱敏文件字段的映射说明；
- 客户/项目负责人确认目标版本的证据编号。

没有明确目标文件时，不得自行猜测“应该长什么样”。

### 2. 提交差异矩阵

新增文档：

```text
modules/moisture/docs/杨总目标表对照与整改说明.md
```

至少逐项比较：

- 工作表名称、数量和顺序；
- 标题、表头、列名、列顺序、合并单元格；
- 原始字段、计算字段和人工填写字段；
- 公式、单位、小数位、日期格式和排序；
- 正常、偏高、偏低、待确认的颜色与文字；
- 汇总口径、供应商/日期/部门分组；
- 图表类型、数据区域、标题和图例；
- 分析结论和人工复核项；
- 当前实现、目标结果、修改位置和验证方法。

### 3. 修复输出实现

在模块目录内调整输出模板或 `reporting/xlsx_writer.py`，不得要求框架修改 Excel。不要修改 `app/`、`core/`、`ui/` 或 `contracts/`。

如果确实需要框架新增交互、输入字段或公共服务，按以下固定目录提交独立框架适配请求：

```text
modules/moisture/docs/framework-change-requests/
FCR-moisture-<YYYYMMDD>-<short-name>.md
```

使用 `docs/handoff/templates/框架适配请求模板.md`，不要直接修改框架代码。

## 三、业务正确性测试由模块负责人完成

至少覆盖：

1. 杨总目标表对应的标准批次；
2. 当前 21 份历史水分 Excel 批量运行；
3. 正常、偏低、偏高、缺年份、缺字段和重复文件；
4. `draft → confirmation → finalize`；
5. 工作表结构、关键单元格值、公式、样式、条件标色和图表数据区域；
6. 输入文件运行前后 SHA-256 不变；
7. 新输出与客户确认目标逐项一致。

不要只比较文件是否生成，也不要使用二进制文件完全相等作为唯一断言。应使用 `openpyxl` 等方式验证工作表语义，并提供人工截图对照。

业务结果是否正确由模块负责人签字确认，框架兼容验收不会替负责人复算。

## 四、重新交付要求

1. 先将最新 `origin/integration` 合并到 `module/moisture`；
2. 只修改 `modules/moisture/`；
3. 更新 `module.json` 版本和 `CHANGELOG.md`；
4. 提交目标表差异矩阵、脱敏黄金样本和自动测试；
5. 推送 `module/moisture`；
6. 创建 `module/moisture → integration` PR，不得指向 `main`，不得自行合并；
7. 通知项目负责人 PR、提交号、模块版本、业务自测结论和回滚版本。

## 五、通过标准

- 模块负责人提供明确、可追溯的客户目标表版本；
- 目标表差异矩阵全部关闭或标明客户接受的差异；
- 21 份历史数据和新增黄金样本的业务测试由负责人确认通过；
- Excel 可打开，结构、关键值、公式、标色和图表符合目标；
- 模块合同、便携运行时和框架兼容测试通过；
- PR 修改范围没有越过 `modules/moisture/`。

框架方最后只出具“兼容通过/不通过”，不出具业务输出正确性结论。
