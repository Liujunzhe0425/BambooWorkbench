## 三、必须整改：可读分析报告

当前实测 `boiling_analysis.md` 约 140 行，其中约 73 行包含 warning/警告信息；41 份历史文件被逐条堆叠，客户难以快速识别重点。PR #38 新增 Excel 报告是积极改进，但不能替代对现有 Markdown 报告的整理。

参考售后分析报告的结构，水煮报告至少包含：

1. **运行概况**：输入、成功、失败、未纳入、待确认；
2. **总体结论**：正常、异常、信息不足和规则冲突数量；
3. **关键指标汇总**：密度、密度差、膨胀率、浸渍剥离，中文名称和单位明确；
4. **异常与待复核明细**：只列异常、冲突、失败和信息不足文件；
5. **AI 辅助分析**：启用时单独展示辅助意见和证据边界；
6. **数据风险**：按类别合并 warning，不逐条重复输出同类技术字段；
7. **建议的下一步**：复测、补字段、核对用途和人工确认建议；
8. **技术附录（可选）**：全部文件明细、规则 ID、来源单元格保留在 Excel/JSON 或附录。

报告不得直接倾倒 `warnings`、机器字段、原始 JSON 或 traceback。正常文件不应逐文件占据主体篇幅。

## 四、必须整改：任务和文件状态语义

任务 15 的实际结果为：

- 输入文件：41；
- `processed_count`：41；
- `failed_count`：0；
- 顶层错误：0；
- 模块任务状态：`partial_success`；
- 37 个文件仅因存在异常/观察项被标成文件级 `partial_success`。

这不符合统一口径。模块必须修正：

- 文件成功完成解析和业务记录生成时，`file_results[].status` 使用 `success`，即使业务结果为异常或需复核；
- 文件损坏、结构无法识别或无法形成记录时才使用 `failed`，并计入 `failed_count`；
- 任务 `failed_count == 0` 且成果生成时返回 `success`；
- 只有同时存在成功文件和真实失败文件时返回 `partial_success`；
- 业务“正常/异常/信息不足/待确认”保留在记录字段、`anomalies` 和报告中，不借用任务执行状态表达；
- 更新现有把“仅有异常而无需回答”断言为 `partial_success` 的测试和文档。

至少加入任务 15 同结构回归：41 个文件全部处理、存在多条异常时，最终任务必须为 `success`。

## 五、必须整改：接入统一 AI 服务

不得在水煮模块内保存 API Key、直接调用 DeepSeek/OpenAI 或要求框架把密钥交给模块。应按以下协议实现：

1. Draft 阶段先完成确定性解析、公式计算和规则筛查；
2. 仅在确有候选时生成 `service_requests`，每个请求具有稳定唯一 `request_id`、`service: "ai"`、清楚的中文 `purpose` 和 `requires_user_consent: true`；
3. Payload 只包含脱敏后的候选 ID、指标名称、观测值、阈值、偏差方向、规则/证据引用和必要上下文，不发送整份 Excel 原文；
4. 声明严格 JSON 响应结构，建议包含 `candidate_id`、辅助摘要、风险等级、复核建议和 `evidence_refs`；
5. 框架负责展示预览、取得用户授权并调用当前配置的 Provider；
6. Finalize 阶段从 `service_response_file` 按 `request_id` 读取响应，先校验状态和 JSON Schema，再应用允许字段；
7. AI 内容只进入报告/Excel 的“AI 辅助分析”区域，不得改写密度、膨胀率、剥离公式、原始值、确定性规则命中或人工结论；
8. 拒绝、无密钥、断网、超时、限流、非法 JSON 和证据不匹配时，继续输出完整离线成果并清楚标注降级原因；
9. Finalize 结果中的 `service_requests` 和 `confirmations` 必须按合同清空。

水分模块现有实现可作为接口行为参考，但本说明已给出完整交互要求，无需复制或修改水分组员代码。

- AI 响应不能改变确定性数值和业务规则结果；
