# 售后分析模块 v1.0.1 整改与重新交付说明

日期：2026-07-22

对象：售后分析模块负责人

分支：`module/after-sales`

允许修改目录：`modules/after_sales/`

目标版本：`1.0.1`

## 一、责任边界与当前优点

当前售后分析报告可作为水分、水煮报告的表达参考。实测报告约 61 行，具有以下优点：

- 先展示运行概况，不把技术字段放在开头；
- 明确一案多标签统计口径，并将案件总数与标签数量分开；
- 使用中文表格汇总月份、案件数和不同费用；
- 单独展示案件处理状态、数据风险和下一步建议；
- 只汇总真实风险，不逐条倾倒全部正常记录或 `warnings`；
- 明确报告不替代责任认定、财务入账、赔偿审批和正式结案。

本轮不要求为报告风格进行无目的重写，负责人应在接入 AI 后保持上述清晰结构。

| 反馈 | 责任方 |
|---|---|
| 售后结构化 JSON 的通用人类查看器 | 框架方；售后模块保持 JSON 合同正确 |
| 售后桌面模块没有 AI 授权项、实际运行离线规则 | 售后模块负责人 |
| 设置、密钥安全、脱敏、逐次授权和 Provider 调用 | 框架方已有能力 |

## 二、必须整改：把售后 AI 接入统一工作台协议

售后源码目前包含自己的 `deepseek_gateway.py` 和进程内 `runtime_config` 直连能力，但统一桌面入口明确不会把 API Key 交给业务模块，且当前返回 `service_requests: []`。因此在竹简工作台中仍是离线规则分析。

本轮应：

1. 桌面模块 Draft 先完成确定性字段提取、规则分类和人工复核候选；
2. 仅为确需辅助分析的案件生成统一 `service_requests`，不得直接读取凭据或发 HTTP；
3. 请求使用稳定 `request_id`、中文 `purpose`、`requires_user_consent: true` 和严格 JSON 响应结构；
4. Payload 只发送脱敏后的投诉摘要、候选类型、规则证据、费用候选及必要上下文，不发送客户身份、联系方式、完整文件或无关原文；
5. 框架展示脱敏预览并由用户逐次允许后调用 Provider；
6. Finalize 从 `service_response_file` 读取并严格校验，按 `request_id` 和案件候选 ID 绑定；
7. AI 可辅助生成问题类型建议、原因摘要、证据说明和复核建议，但不得自动作出责任认定、费用审批、赔偿决定或结案；
8. 现有强制人工复核仍保留，AI 不能绕过售后费用、责任工厂和投诉类型的人工确认；
9. 拒绝、无密钥、断网、超时、限流或非法响应时自动使用离线规则结果，不能使整批失败；
10. 最终报告和 Excel 明确标注“AI辅助完成/离线规则完成/AI降级”，但保持现有简洁报告结构。

独立网站如仍需保留直连网关，必须与统一桌面入口清楚隔离，并用测试证明桌面运行不会访问模块自己的网关或凭据。

## 三、推荐的结构化响应字段

每个案件的 AI 响应建议只包含：

- `candidate_id`：稳定脱敏候选 ID；
- `issue_types`：性能/外观/加工/其他的候选多标签；
- `primary_issue_type`：建议主分类；
- `reason_summary`：简短原因摘要；
- `evidence_refs`：只能引用请求中提供的证据编号；
- `review_suggestion`：供人工复核的建议；
- `confidence`：辅助置信度。

费用、责任、关闭状态等高风险字段必须继续使用规则和人工确认，不因模型置信度高而自动通过。

## 四、结构化明细与报告要求

`after_sales_records.json` 继续作为机器合同，不为界面美观删减审计字段。客户主成果仍是 Excel 和现有风格的 Markdown；框架会提供通用 JSON 人类视图。

接入 AI 后报告仍应保持：运行概况、问题类型、月度案件与金额、处理状态、数据风险、下一步建议六类业务信息，不直接倾倒模型原始响应或大段 JSON。

## 五、自测与通过标准

至少覆盖：

- 标准案件、多标签、费用、责任、未结案、缺字段和损坏文件；
- AI 有候选并允许、拒绝、无密钥、超时、非法响应和证据引用错误；
- AI 不能跳过三项强制人工复核；
- 离线与 AI 降级均能生成 Excel、Markdown、JSON 和年度汇总；
- 桌面入口不直接读取 API Key、不直接调用模块自带网关；
- 合同、模块测试、Ruff、`version`、`self-check`、便携 `draft → finalize` 通过；
- 售后负责人确认多标签、费用和人工复核后的业务结果正确。

## 六、重新交付方式

1. 同步最新 `origin/integration`；
2. 将模块全部活动版本元数据更新到 `1.0.1`；
3. 只修改 `modules/after_sales/`；
4. 更新 `CHANGELOG.md`、AI 服务请求/响应实现、测试和脱敏证据；
5. 推送 `module/after-sales`；
6. 创建或更新 `module/after-sales → integration` Draft PR，不得指向 `main`，不得自行合并；
7. 通知项目负责人 PR、提交号、测试结果、AI 允许/拒绝/降级证据和回滚提交。
