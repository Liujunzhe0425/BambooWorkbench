## 二、框架已批准修复要求

### FW-UI-101：确认项字段中文化

- 将 `arrival_date` 显示为“到货日期”，`test_date` 显示为“检测日期”；
- `arrival_date/test_date` 显示为“涉及日期：到货日期、检测日期”，不再使用“位置”描述机器字段；
- 保留合同中的原始字段名，只改变 UI 文案；
- 未知机器字段使用安全回退，不影响既有水煮和售后确认项。

### FW-AI-101：AI 授权采用渐进式披露

默认界面只显示：

1. 为什么需要联网，例如“复核 3 条水分规则候选”；
2. 将发送什么，例如“仅发送脱敏后的指标、阈值、偏差方向和规则引用，不发送 Excel 文件原文”；
3. 发送到哪里，例如当前配置的提供商和模型；
4. “允许/拒绝”选项，默认仍为“拒绝”；
5. 一个“查看发送明细”小三角，展开后才显示格式化、可滚动、可复制的脱敏 JSON。

不得删除逐次授权、脱敏预览、API Key 隔离、请求审计或拒绝后的离线降级能力。不得用“已脱敏所以安全”等绝对化表述。

### FW-VIEW-101：结构化明细的人类视图

当前 `.json` 是模块与框架之间的可追溯机器合同，设计上必须保留，不能为了美观改变其语义或删除审计字段。问题在于框架目前只做 JSON 缩进后全文展示，不适合作为客户主视图。

框架应：

- 默认展示任务概况、记录数量、关键业务字段和异常/失败摘要；
- 记录较多时使用表格或分组卡片，可搜索、滚动和按文件展开；
- 使用中文标签、单位和空值说明；
- 将原始 JSON 放入默认收起的“技术明细/原始 JSON”区域；
- 不修改磁盘上的原始 JSON，不自行推断模块业务结论；
- 把按钮文案区分为“查看业务明细”和“查看技术 JSON”。

模块负责人仍须提供清晰的 Excel/Markdown 主成果；JSON 不应成为唯一面向客户的报告。

### FW-RESULT-101：失败文件展开列表

结果摘要的“失败 N”右侧增加小三角：

- 默认收起，避免大量文件占满页面；
- 展开后逐条显示文件名和一行失败原因；
- 优先使用 `file_results[].error`，不得显示本机绝对路径、Python traceback 或内部异常对象；
- 常见原因使用客户可理解的分类：文件损坏/不是有效 Excel、模板或字段结构不符合要求、不支持的格式、读取失败；
- 无公开原因时显示“未能完成处理，请查看日志或联系技术人员”，保留技术日志追踪入口；
- 支持部分成功任务，不把一个坏文件误显示为整批全部失败。

### FW-STATUS-101：统一“已完成/部分完成/失败”语义

客户实测任务 15（水煮实验）为：输入 41、成功处理 41、失败 0、错误 0，但模块返回任务级 `partial_success`；其中 37 个文件只是存在业务异常或观察项，被错误标成文件级 `partial_success`。历史页只是如实展示模块状态，因此根因是模块状态语义错误，同时框架缺少统一一致性校验。

统一口径：

- **已完成（success）**：没有任何输入文件处理失败，最终成果已生成；允许存在业务异常、规则命中、观察项、人工复核结论或 AI 降级；
- **部分完成（partial_success）**：至少一个输入文件处理成功，同时至少一个输入文件实际处理失败，即 `failed_count > 0`；
- **失败（failed）**：没有形成可用业务成果，输入全部失败或任务发生不可恢复错误；
- **待确认（needs_confirmation）**：只用于尚未完成必要人工确认的中间状态，不作为最终“部分完成”的替代。

框架应在保存和展示终态前校验：

- `failed_count == 0` 时不得显示 `partial_success`；
- `partial_success` 必须存在至少一个 `file_results[].status == failed`，且同时存在可用处理结果；
- 业务异常和规则判定应放在 `anomalies`、业务状态或报告中，不改变文件是否成功处理；
- 对旧任务可在界面按 `summary.failed_count` 和 `file_results` 计算正确的显示状态，但不得篡改历史 `result.json`；
- 发现新模块结果语义冲突时记录诊断信息并安全归一化显示，不能因此丢失成果或把任务改成失败。

### FW-OUTPUT-101：输出目录真正生效

当前设置页只保存 `output_dir`，任务仍固定写入应用数据目录。修复时必须保持模块沙箱：模块仍写入任务内部 `output-final`，任务成功或部分成功后由框架复制/发布成果到用户指定目录。

目标目录格式：

```text
<用户输出目录>/
  <六位任务编号>-<任务类型>-<YYYYMMDD-HHMMSS>/
    <该任务全部最终成果文件>
```

例如：

```text
000123-竹丝水分-20260722-143015/
```

要求：

- 每个任务独立文件夹，编号稳定，任务类型使用安全中文名称；
- 文件夹冲突时不得覆盖旧成果，应追加安全后缀或报告错误；
- 输出目录为空时继续只保存在应用本地任务目录，并在设置页解释该含义；
- 目标不可写、磁盘空间不足或复制失败时，内部成果不得丢失，结果页应给出明确提示；
- 不把用户指定目录直接交给模块进程，避免破坏路径隔离和可追溯性。

### FW-NAV-101：统一返回按钮

- 除工作台首页外，任务创建、任务进度、待确认、结果中心、任务历史、知识库和设置页均提供一致的“返回”按钮；
- 返回上一实际页面，而不是一律跳首页；
- 任务运行、确认提交和结果打开过程中不得丢失当前任务状态；
- 没有有效上一页时回到工作台首页；
- 侧栏直接导航仍可使用，返回栈不得产生循环跳转。

### FW-HOME-101：正式版首页去开发化

正式运行模式删除或改写：

- “框架准备度”；
- “模块接入 3/3”；
- “正式/演示/待接入”统计；
- “统一入口承载三个业务模块”；
- “已加载 3 个正式业务模块，可直接处理文件并生成成果”；
- 模块卡片中的“已安装 · 正式模块 · 健康”。

正式版仅保留企业名称、产品名称、三个业务入口及必要的离线/联网状态。显式 `--demo` 模式仍可显示“演示模式”，缺失模块仍需显示“暂未安装”。

## 三、框架验收标准

1. 上述七项框架功能均有 UI/集成回归测试；
2. 三模块合同、任务隔离、历史任务和人工确认流程不回归；
3. 输出目录测试覆盖空值、正常复制、同名冲突、不可写目录和部分成功；
4. 失败文件列表覆盖损坏文件、结构不符和未知错误；
5. 状态语义测试覆盖“有业务异常但无失败＝已完成”“成功与失败混合＝部分完成”“全部失败＝失败”，并使用任务 15 同结构结果回归；
6. AI 技术预览默认收起，但授权前始终可以查看完整脱敏内容；
7. 完整仓库门禁、便携包和安装生命周期验证通过。

## 五、框架实施与验证结果

已完成：

- `FW-UI-101`：日期字段只在 UI 翻译为“到货日期/检测日期”，合同字段保持不变；
- `FW-AI-101`：授权默认显示业务摘要，完整脱敏 JSON 通过小三角展开并可复制；
- `FW-VIEW-101`：JSON 默认展示中文业务表格，“技术 JSON”作为独立次级页保留；
- `FW-RESULT-101`：失败数量右侧可展开文件名和公开简短原因，不展示绝对路径或 traceback；
- `FW-STATUS-101`：新任务在持久化前按实际文件失败归一化，旧任务只修正显示而不改写证据；
- `FW-OUTPUT-101`：模块仍写内部沙箱，框架完成后复制到编号隔离的用户输出目录；复制失败保留内部成果并提示；
- `FW-NAV-101`：所有非首页流程使用统一返回按钮和真实访问历史栈；
- `FW-HOME-101`：正式首页移除准备度、正式模块健康等开发诊断文案，显式演示模式和缺失占位仍保留。

验证结果：

- 框架主测试：`347 passed, 8 skipped`；8 项均因当前 Windows 用户缺少创建符号链接权限而按原设计跳过；
- 售后模块兼容测试：`43 passed, 3 skipped`；
- 水煮模块兼容测试：`39 passed`；
- 水分模块兼容测试：`353 passed`；
- Ruff、模块合同校验和 `git diff --check` 通过；
- 本轮未修改三个真实业务模块的公式、阈值、分类规则或业务报告内容。
