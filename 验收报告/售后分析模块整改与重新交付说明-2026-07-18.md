## 三、必须修改的问题

### AS-01：离线模式产生重复且无意义的人工确认

#### 当前问题

模块在正常离线模式下，会为每一份 Excel 生成一条：

```text
未配置API，问题类型使用关键词规则粗略判断
```

13 份历史文件因此产生 13 条相同 `api_config` 确认，整个任务被置为 `needs_confirmation`。即使数据没有业务歧义，用户也必须再确认一次“继续使用离线规则”才能生成最终结果。

这违背了竹简工作台减少重复人工操作的核心目标。

#### 修改要求

1. 当 `ai_enabled=false`，或框架没有提供已授权的 AI 服务响应时：
   - 直接使用确定性离线规则完成任务；
   - 不生成 `api_config` 人工确认；
   - 不得因为没有 API 把任务置为 `needs_confirmation`。
2. 没有真实业务歧义时，任务状态必须直接为 `success`。
3. 只有具体业务字段存在歧义时，才生成对应字段的确认，例如：
   - `complaint_date`
   - `fee_amount`
   - `brand`
   - `issue_types`
   - `resolution_status`
4. “AI 未启用、已使用离线规则”可以写入运行说明或日志，但不是人工确认项。
5. 将用户可见的“规则回退完成”改为更清楚的“离线规则分析完成”。

#### 达标标准

- 一份字段完整且无歧义的脱敏样表，离线运行后直接返回 `success`，确认项为 0。
- 多文件批次只产生真实业务歧义对应的确认，不得按文件重复产生 `api_config` 确认。
- 13 份历史数据重新运行时，不再出现 13 条“未配置 API”确认。

### AS-02：费用没有按业务口径分成三类

#### 当前问题

模块目前只有一个 `fee_amount/cost` 字段，不能区分：

1. 企业实际售后成本；
2. 内部责任扣款；
3. 供应商、合作方等外部承担金额。

这三类金额的性质不同，不能混合统计。

#### 修改要求

在结构化明细和 Excel 中分别保存：

| 建议字段 | 含义 | 是否计入企业售后成本 |
|---|---|---|
| `enterprise_cost_amount` | 企业实际承担的补发、返工、赔偿、运费、人工、差旅等成本 | 是 |
| `internal_accountability_amount` | 内部人员或部门责任扣款 | 否，单独统计 |
| `external_borne_amount` | 供应商、合作方或其他外部主体承担的金额 | 否，单独统计 |

每类金额还需有：

- 金额状态；
- 原文依据；
- 是否经过人工复核；
- 无法确定时保持空值，不使用 0 代替未知。

为兼容旧字段，可暂时保留 `fee_amount`，但其含义必须明确等同于 `enterprise_cost_amount`，不得再表示三类费用的混合值。

汇总页原来的“费用”应改名为“企业售后成本”，并增加“内部责任扣款”和“外部承担金额”的独立统计区域或工作表。

#### 达标标准

- 同一文件同时出现售后成本和内部扣款时，两者进入不同字段，不能相加。
- 明确由供应商承担的费用进入外部承担字段，不计入企业售后成本。
- 未知费用保持空值并生成具体费用字段的复核项。
- 三类费用的明细合计与汇总表完全一致。

### AS-03：缺少图表、分析报告和业务建议

#### 当前问题

当前只输出：

- `after_sales_summary.xlsx`
- `after_sales_records.json`
- `result.json`

没有售后趋势图、问题类型图、品牌对比图，也没有可供业务人员直接阅读的正式分析报告和建议。

#### 修改要求

1. 在 `after_sales_summary.xlsx` 中增加“分析图表”工作表，至少包含：
   - 月度售后案件数量趋势图；
   - 品牌或问题类型分布图；
   - 企业售后成本趋势或分布图。
2. 新增：

```text
after_sales_analysis.md
```

3. 分析报告至少说明：
   - 输入文件数、成功数、失败数和待复核数；
   - 主要问题类型及变化；
   - 售后成本较高的月份或类别；
   - 未关闭、处理中和待确认案件；
   - 数据缺失、费用冲突等风险；
   - 可执行但不越权的复核建议。
4. 图表和分析必须来自结构化统计结果，不得编造数据。
5. 建议不得自动认定责任方、赔偿金额、审批结果或正式结案。
6. 在 `result.json.outputs` 中登记新增的分析报告。

#### 达标标准

- Excel 打开后可以直接看到清晰的图表，标题、图例、单位和数据范围正确。
- Markdown 分析报告中的案件数、费用数和状态数与 Excel、JSON 一致。
- 空数据或部分失败时仍可生成解释清楚的报告，不出现空白图表或程序异常。

### AS-04：多问题类型的文档与汇总逻辑不一致

#### 当前问题

README 写明“一条售后可同时计入多个类型”，结构化记录也保留多个 `issue_types`；但统计 Excel 只按 `primary_issue_type` 计数。

例如同一案件同时存在“开裂”和“尺寸错误”，明细会包含“性能、加工”，但汇总只计入其中一种。

#### 已确认的正式口径

- 案件总数按文件/案件去重，每个案件只计 1 次；
- 性能、外观、加工三个分类分别按标签统计，同一案件可以进入多个分类；
- 因此三个分类数量相加允许大于案件总数；
- 同时保留 `primary_issue_type`，用于展示最主要原因；
- Excel 必须注明“分类为多标签统计，不能直接相加作为案件总数”。

该口径已由项目负责人于 2026-07-18 明确确认。请按此实现，并确保 README、规则文档、测试和代码完全一致，不得自行改回只按主要类型统计。

#### 达标标准
