## 3. 必须整改的问题

### P0-1：离线模式产生无业务价值的重复确认

模块在没有 API 的正常离线模式下，为每个输入文件生成一条 `api_config` 确认项。13 份历史表因此产生 13 条相同确认，整个批次状态被置为 `needs_confirmation`。

单文件通过竹简工作台运行时，即使字段、费用和状态都可正常分析，任务仍停在 `waiting_confirmation`；用户必须人工提交“继续使用离线规则”后才能生成最终结果。

整改要求：

- `ai_enabled=false` 或框架没有授权 AI 服务时，不得生成“未配置 API”人工确认；
- 离线规则分析应直接完成；
- 只有具体业务字段存在歧义时才生成对应字段的确认；
- 不得把普通降级说明作为阻断任务状态的确认项；
- 新增单文件和批量离线模式回归测试，确保无真实歧义时状态为 `success`。

### P0-2：费用没有按已确认口径分开

当前只有单一 `fee_amount/cost` 字段，未分别输出：

1. 企业实际售后成本；
2. 内部责任扣款；
3. 供应商/合作方等外部承担金额。

整改要求：三类金额、依据、是否纳入企业成本必须分别保存和展示；不得直接混加。历史单一“费用”汇总应明确改名为“企业售后成本”。无法确认的金额保持空值并进入具体字段复核。

### P0-3：缺少客户预期的图表和分析建议

当前只输出统计 Excel、结构化 JSON 和一条运行计数摘要，没有售后趋势图、问题类型图、品牌/月度变化图，也没有可供业务人员阅读的分析报告和处理建议。

整改要求：至少提供：

- 月度售后数量趋势；
- 品牌或问题类型分布图；
- 企业售后成本趋势或分布；
- 一份可追溯的 Markdown 或 Excel 分析页，说明主要问题、异常变化、待人工复核项和建议；
- 自动建议不得越权认定责任、赔偿或正式结案。

### P1-1：多问题类型的文档与实际汇总矛盾

README 说明“一条售后可同时计入多个类型”，结构化明细也保留多个 `issue_types`；但汇总表只按 `primary_issue_type` 计数。历史数据中同一案件同时含性能与加工问题时，次要类型不会进入分类汇总。

最终规则需由项目负责人确认。推荐口径：案件总数去重计 1；性能/外观/加工分类分别按标签计数，因此分类合计可以大于案件总数；同时保留一个主要类型字段。

### P1-2：结构化明细 Excel 泄露本机绝对路径

“输入文件对账”和“待人工确认”页已只显示文件名，但“售后明细”页仍写入完整 `source_file` 绝对路径。

整改要求：面向用户的 Excel、Markdown 和 JSON 默认只展示文件名或任务内相对路径；完整本机路径只允许保留在受控本地审计数据中，不得进入可外发报告。

### P1-3：损坏文件错误信息不够友好

损坏 Excel 当前直接显示英文底层错误 `File is not a zip file`。

整改要求：转换为稳定错误码和中文提示，例如“工作簿损坏或不是有效的 XLSX 文件”，技术异常仅写本地日志，不向业务界面显示 traceback。
